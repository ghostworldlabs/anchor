Crucible Stage 1 — Master Plan DRAFT (unapproved)

# Master Plan (draft)

**North Star:** A project in Anchor is stood up, planned, and driven BY TALKING TO ITS STEWARD. John describes the project in his own words; the steward compiles that description into the project's Face and Campaign Roadmap, proposes a commission for a named roadmap step, and - only on John's explicit confirmation - Anchor executes it as a real trio run. The produced plan comes back as an artifact John can read on screen and change by talking; when he says start, Foreman executes and the Roadmap shows the truth about what is running. Nothing is spent, written, or started without a human confirmation, and the campaign ledger remains the single source of truth. NON-GOALS: portfolio altitude (High Seat cross-project reporting, pause, resource conflicts) is deferred; no changes to Crucible/Foreman/researchPrime themselves; no bespoke plan template (the Crucible plan shape IS the template); no steward persona/livery, mobile/iPad; nothing that makes the steward do the planning itself rather than commission it.

## Success criteria
- Fresh start: from a project with no Face, no Strip and no roadmap, a spoken description produces a Face north-star AND at least one roadmap step, with ZERO chat turns persisted (E5: Strip receipts + roadmap events + Face narrative are the sole durable ledger; the dialogue COMPILES into the Face via refine_goal -> face_rewrite_receipt). Every compile that spends money is itself proposed and confirmed at a shown estimate first - the spend invariant governs the compiler exactly as it governs a commission.
- Propose/confirm, in TWO BEATS: (a) CONFIRM-TO-PLAN - a planning commission is proposed FOR a named roadmap step (never free-floating), showing skill + seat + depth + estimate BEFORE any spend; nothing runs until John confirms, and the confirmation records `who`. (b) CONFIRM-TO-BUILD - an approved plan artifact NEVER auto-flows into a build; a second, distinct confirmation bound to a specific plan artifact VERSION is what launches Foreman. The Roadmap step's live status names which beat is running (PLANNING / BUILDING) so 'what is running' is never ambiguous between the run that produced a plan and the run executing it. The engine halves this rests on are HYPOTHESES gated in Wave 1 - see G1 below.
- Real execution + validated handback: Anchor executes the confirmed commission as a real trio run on the real substrate and returns a handback that is validated against the required set (active_effort, why_next, grasscatch_why, tool_depth_why, human_wait, uncertainty_flags); a malformed handback is REFUSED, never absorbed. That the substrate (job_runner.py / terminal_session.py / lanes.py) and receipt-validate.mjs can do this is a HYPOTHESIS gated in Wave 1 - see G3 and G4 below.
- Reviewable artifact + spoken refine: the produced plan renders as a readable on-screen artifact and a spoken correction produces a new version through the SAME propose -> confirm path. That packet-view.mjs classifyArtifact/buildArtifactCard can render a real converged doc-trio is a HYPOTHESIS gated in Wave 1 - see G2 below.
- Honest status: the Roadmap step status reflects the ACTUAL state of the Anchor session across park (STATUS_IDLE), restart and kill - it never reports work that is not running. Status flows as status_flip events; the projection derives.
- Auth-ON proof: every criterion above passes with ANCHOR_TOKEN set, asserted on OUTCOMES not plumbing. This surface shipped broken twice in one week because effectively the whole Anchor suite runs auth-off.
- Single writer, proven: roadmap_events has exactly ONE writer, proven by a concurrency test (hardening law: a durability claim is a STORAGE claim - name atomic write + lock/serialization + a concurrency test), not by prose. Anchor must not become a second writer.

## Wave-1 ground-truth gates (these are HYPOTHESES, not facts)

Nothing in the success criteria may be read as a claim about code that exists today. Each hypothesis below is a Wave-1 PASS/FAIL gate carrying a named replan branch and the degraded product shape John actually gets if it fails. An ungated hypothesis is not evidence, and no phase after Phase 1 may cite one as a reason to skip work.

- **G1 - the commission halves.** HYPOTHESIS: job-lifecycle.mjs proposeCommission (~:141) / confirmCommission (~:250) exist and can carry a roadmap-step binding and a `who`. PASS = the Wave-1 executability test drives them to a real OS process and a returned handback. FAIL = Anchor builds the commission lifecycle as new code against the same event contract (+1 wave). DEGRADED SHAPE: v1 ships the PLAN beat first and the BUILD beat moves to the final phase.
- **G2 - artifact rendering.** HYPOTHESIS: packet-view.mjs classifyArtifact/buildArtifactCard renders a real converged Crucible doc-trio readably. PASS = the Wave-1 spike verdict on this project's own Stage-2 output is pass, recorded verbatim. FAIL = a plan-shaped classifier and renderer enter scope. DEGRADED SHAPE: v1 shows the plan as a navigable section list, with no diff view and no deep links.
- **G3 - handback validation.** HYPOTHESIS: receipt-validate.mjs enforces the required set (active_effort, why_next, grasscatch_why, tool_depth_why, human_wait, uncertainty_flags). PASS = a real trio handback validates and a deliberately corrupted one is refused, both observed. FAIL = Anchor owns validation. DEGRADED SHAPE: the required set shrinks to the fields the derivation map can honestly fill, and the shrink is published rather than hidden.
- **G4 - the real substrate.** HYPOTHESIS: job_runner.py / terminal_session.py / lanes.py can launch and own a real trio run end to end. PASS = observed pid plus returned handback. FAIL = the vertical slice launches the trio directly and substrate integration becomes its own phase. DEGRADED SHAPE: one run at a time, no lane multiplexing.
- **G5 - HALT traversability.** HYPOTHESIS: every human gate on the commission's real code path can be surfaced and resumed WITHOUT changing the trio. PASS = the Phase-1 classification table shows no requires-trio-change and no invisible HALT on the chosen path. FAIL = the supported path is restricted to the gate profiles that survive. DEGRADED SHAPE: v1 commissions only those profiles, and the excluded ones are named in the Face.
- **G6 - identity.** HYPOTHESIS: ANCHOR_TOKEN carries a recoverable subject. PASS = a subject is extracted from the credential in this wave. FAIL = `who` is recorded honestly as unattributed(shared_secret). DEGRADED SHAPE: v1 attribution reads 'the holder of this box's token', stated plainly in the UI, and no identity provider is built.

## The spend invariant is NOT amended by this plan

The North Star's wording governs verbatim: **nothing is spent, written, or started without a human confirmation.** No phase in this plan softens it in place; any phase text that appears to is a defect, not a design decision.

The uncomfortable consequence is designed for rather than argued away: **a Face compile is a spend, so it sits behind confirm-before-spend exactly like a commission.** The steward shows what it intends to compile and at what estimate, John confirms, the compile runs, the diff comes back (Phase 4). Steward behaviour that spends nothing - parsing, classification, the commissionability predicate, the dry-run proposal - requires no confirmation precisely because it is free, and Phase 5 ships the test proving the proposal path spends zero.

**AMENDMENT PROPOSAL - recorded here, NOT applied, John's decision alone.** If per-compile confirmation proves to make conversation genuinely unusable, the single proposal on the table is a *confirmed compile envelope*: John confirms a bounded budget once at the start of a describe session; the steward may spend only inside it; every compile is still shown; envelope exhaustion is a hard stop requiring a fresh confirmation. Its PREREQUISITE is the Phase-1 empirical compile-cost measurement (median and p90 dollar cost, wall clock, and confirmations-per-useful-Face-version over >= 20 real compiles). Until John accepts this amendment in writing it is not scheduled, not assumed, and not partially implemented - every phase and the Phase-9 demo assert the UNAMENDED invariant.

## Two beats, two confirmations (decided in Phase 1, asserted in Phase 9)

The roadmap-step-type -> skill -> confirmation-type map is fixed for v1: a RESEARCH step commissions researchPrime, a PLAN step commissions Crucible, a BUILD step commissions Foreman. **CONFIRM-TO-PLAN** is bound to a roadmap step ULID and launches a Crucible planning run. **CONFIRM-TO-BUILD** is a separate confirmation bound to an approved plan artifact VERSION and launches Foreman on it; amending the plan invalidates any outstanding build proposal. Roadmap status truth attaches to whichever run is live, with the beat named, and derives from the same lease + status_flip projection for both.

Nine phases, front-loaded so that every assumption this North Star rests on is proved empirically before anything is built on top of it - and so that the first end-to-end proof arrives in Phase 3 rather than in the last wave. Phase 1 is a ground-truth wave: hammer the storage primitive on the actual Windows box, audit and actually execute the claimed engine halves (G1), classify every HALT in the real trio code path and state a gate budget, spike a real converged doc-trio through packet-view.mjs (G2), measure what a compile actually costs, resolve what ANCHOR_TOKEN's identity actually is (G6), decide the two-beat confirmation map, flip auth ON while the suite is small, and fence the trio trees with a CI diff guard. Phase 2 builds the ledger spine (append-only, single-writer, partitioned per project, one dossier key per commission lifecycle). Phase 3 is the UGLY VERTICAL SLICE: describe -> propose -> confirm -> a real process -> a real artifact on screen, with lease-based status truth shipping in the same phase as the first real execution. Phase 4 replaces the slice's provisional extraction with the real Face compiler - a projection over face_events with verbatim source_text, provenance spans, a visible dropped_or_generalized diff, first-class retraction, and a bounded, confirmed, metered compile. Phase 5 makes commissionability a unit-tested predicate bound to an immutable step ULID, with a genuinely free dry-run proposal. Phase 6 hardens the confirm-to-live-truth path with an intent record, a durable launcher, a run-scoped capability, a sweeping lease reconciler and a fsync'd outbox, adds the distinct build-beat confirmation, and proves gate-surfacing on a deliberately gate-heavy real Crucible commission. Phase 7 makes the handback repairable-then-validated, with provenance-cited fields, typed unavailable(reason), and a published honest-coverage ratio. Phase 8 delivers the readable artifact and the spoken correction as a typed, lineage-tracked amendment through the same propose->confirm path. Phase 9 makes the whole North Star one runnable, auth-on, outcome-asserted demo script asserting BOTH beats. Every phase names what it defers rather than dropping it silently; the North Star's non-goals (portfolio altitude, High Seat, pause, resource conflicts, trio modification, bespoke plan template, persona/livery, mobile, ASR) are never scheduled at all.

- Line-by-line audit of job-lifecycle.mjs proposeCommission (:141) and confirmCommission (:250), producing a checked-in table of the ACTUAL parameters and return shape, with explicit findings on (a) whether a roadmap-step binding field exists and (b) whether a `who` field exists. No assumption that they 'have or can take' them. (I24, M20)

## Phase 2 â€” Phase 2 - The ledger spine: one writer, one dossier key, invariants in CI

Serves criterion 7 directly and is the precondition for criteria 1, 2, 3 and 5. Every later guarantee is a claim about storage. Building the single-writer fence, the typed foreign keys and the lifecycle join key now costs one wave; backfilling them across seven stores after the first wrong DONE is not affordable.

**Near-term specifics:**
- Stand up the append-only stores chosen in Phase 1: roadmap_events, face_events, source_text blob store, and the commission dossier - all under the Phase-1 hardening-law primitive.
- Make the second writer physically impossible: the events store is writable only by a process holding a named lock/socket that job_runner.py cannot acquire, or writes go through an IPC endpoint with no file path exposed to Python. Plus a CI check that greps the Python tree for any reference to the events file path and fails the build. (I41, M13)
- Single-writer concurrency test that fails if either the atomic-write primitive or the lock is removed - the proof the criterion demands, not prose. (I43, criterion 7)
- Typed foreign key: the commission -> step binding is validated on write against the step store; a commission whose step ID does not resolve is REJECTED at write time. (I18, M21)
- Bidirectional integrity sweep, run periodically and in CI: commissions pointing at dead steps, and steps pointing at runs that never launched. (I18)
- The COMMISSION DOSSIER: one record joining step ULID -> proposal -> confirmation (with who + human|synthesized provenance) -> minted capability -> process/lease -> quarantined handback -> validated receipt -> artifact version -> spend. One key for the whole lifecycle, created in this phase so nothing later has to backfill it. (I49)
- Type confirmations at the storage layer: every approval event records actor identity plus human|synthesized provenance. A synthesized human approval becomes a schema-level impossibility rather than a policy. (I19, M10)
- Ledger invariant checker, runnable in CI and periodically in production: referential integrity both directions, single-writer attestation, no live RUNNING without a live lease, no synthesized human approval in any confirmed chain, no receipt field without a source pointer. Clauses land as their phases land; the checker exists from here. (I50)
- Per-project event streams are PARTITIONED at the storage layer so the shared surface is structurally near-zero. That partition is the whole of v1's cross-project work: no cross-project write path is built, and the two-live-session concurrency test is scoped to proving the partition holds (two sessions on two projects cannot touch one another's stream), not to arbitrating a shared write. A shared-write transaction re-enters through the Grasscatcher only when a concrete single-project failure mode is named for it; none is on the table today. (I44, M28)
- Zero-chat-turn conformance as an ALLOW-LIST assertion over storage keys: the durable stores may contain only Strip receipts, roadmap events, face_events and source_text artifacts. A future 'temporary' transcript sink fails the build. (I13, criterion 1)

**Deferred (explicitly):**
- Cross-project VIEWS, High Seat reporting, pause and resource-conflict arbitration - North-Star non-goals, not scheduled.
- Event-log retention, compaction and archival policy - v1 keeps everything.
- Multi-user identity and per-user authorization beyond John as the single principal.

## Phase 3 â€” Phase 3 - The ugly vertical slice: describe, propose, confirm, real process, something on screen

Serves criteria 1, 2, 3, 4 and 5 at the lowest fidelity that is still real. The premortem's quietest failure is a plan whose first end-to-end proof lands in the final wave, by which point every integration surprise re-plans five finished phases. This phase is UGLY BY CONTRACT - hard-coded strings, one project, one commission, no diff view, no sharpening loop, no retraction - but it may not be FAKE: the process is real, the handback is real, the status is derived from liveness, and the artifact on screen came out of a trio run's output bundle. It is also where the two-beat shape and the spend invariant stop being prose.

**Near-term specifics:**
- One end-to-end path, hard-coded wherever that saves a wave: typed description -> ONE compiled Face field and ONE roadmap step (no compiler yet; a minimal extraction is allowed and must be labelled PROVISIONAL in the UI) -> a proposal card for that step -> John's confirmation -> a real Crucible planning run on the real substrate -> a real handback -> the plan visible on screen.
- Both confirmation beats exist from this phase onward. CONFIRM-TO-PLAN launches Crucible for real. CONFIRM-TO-BUILD may be stubbed here to an explicit refusal that names the plan artifact version it WOULD have built - but the two-beat shape is proven now, never retrofitted, so a plan handback can never quietly become a build.
- Every spend on this path is proposed and confirmed at a shown estimate, including the provisional compile, per the governing spend invariant. The slice is where the unamended invariant is first proved end to end and where the Phase-1 compile-cost measurement becomes a number John experiences rather than reads.
- STATUS TRUTH SHIPS HERE, not in a later hardening phase: the run renews a lease, the UI renders RUNNING only while the lease is live, and a kill -9 during the slice produces STALE rather than a lying RUNNING. Minimal mechanism, correct semantic. (I38, M16, criterion 5)
- The artifact on screen must originate from the run's output bundle (artifact hash present in the bundle); a steward-authored stand-in fails the slice. The North Star's most likely drift gets its guardrail at the first render, not at Phase 8. (I52)
- Runs against the Phase-1 HALT classification table: the slice's commission profile is chosen from the externally-observable class only, and the wave report states how many human gates the real path actually cost against the stated gate budget.
- Wave report records, from the real path: end-to-end wall clock, dollar cost, confirmations required, artifact readability verdict, and every place the path broke. This is the empirical input that re-plans Phases 4-9 BEFORE they are built.

**Deferred (explicitly):**
- Everything that makes it good: the real Face compiler and provenance (Phase 4), commissionability and sharpening (Phase 5), capability minting, outbox, durable launcher, sweeping reconciler and gate-surfacing (Phase 6), handback provenance validation (Phase 7), the readable artifact and typed amendments (Phase 8).
- Multi-project, multi-commission and concurrent runs - the slice is one project, one commission, one run.
- Any claim that the slice is shippable. It is a proof; its UI is thrown away and its provisional labels are load-bearing until Phase 4 replaces them.

## Phase 4 â€” Phase 4 - The Face as a compiled projection, with the source text kept

Serves criterion 1. The failure this phase exists to prevent is executing a paraphrase for three weeks: a compile that silently drops a constraint is indistinguishable from one that kept it unless the raw sentence survives and the compiler shows what it did not keep. Making the Face a projection over face_events reuses the roadmap's storage discipline instead of inventing a second one.

**Near-term specifics:**
- Persist John's raw typed description as an immutable, content-hashed `source_text` ledger artifact keyed to the Face version it produced. One blob per description. (I1, M1)
- Give every compiled Face field a provenance span (source_hash + char offsets) back into the source text. (I1)
- Property test over N generated descriptions: from any Face version, the exact source text is reproducible byte-identically from the ledger. Not a single fixture. (I3, M1)
- Face becomes a projection over an append-only face_events log with typed events assert / retract / refine, each carrying source text, actor and timestamp. The Face document is derived, never mutated in place. (I4, M3)
- Every compile emits an explicit `dropped_or_generalized` list - what the compiler did NOT keep and what it widened - rendered as part of the proposal. The Face version is not accepted until John has seen that list. (I2, M1)
- Retraction as a first-class persisted event that PRESERVES the retracted content plus a `why`; the compiler consults retractions as a hard exclusion set on every recompile. Test: a retracted goal never reappears across N recompiles seeded with the original description. (I6, M4)
- Park/restart equivalence test: apply correction C mid-session, and apply the same C after a park+restart from the same starting state; assert byte-identical resulting Face projection. Drift is a hard test failure, never a judgement call. (I5, M3)
- Bound the compile: max rewrite passes per turn, a fixed-point check (unchanged Face -> stop), and a circuit breaker that HALTs and asks John when the compiler cannot converge. (I9, M6)
- Face rewrites are incremental and diff-based - `refine` events touching named fields - never whole-document regeneration. Cheaper per correction, produces a reviewable diff for free, and removes the mechanism by which roadmap regeneration orphans live commissions. (I10, M5)
- Cost ledger: every compile invocation logged to the durable ledger with token count and dollar estimate, so a runaway is diagnosable after the fact. (I54, M6)
- CONFIRM-BEFORE-COMPILE: every compile that spends is proposed first - what it will compile, at what estimate - and runs only on John's confirmation, exactly as a commission does. The Strip's running conversational-spend number is OBSERVABILITY, not authorization: there is no soft threshold and no unconfirmed spend below a line. If the Phase-1 measurement and the Phase-3 slice show this is unusable in practice, the answer is the separately recorded amendment proposal and John's written decision - never an in-phase softening. (I11, M5)
- The whole flow compiles through refine_goal -> face_rewrite_receipt with zero chat turns persisted, asserted against the Phase-2 allow-list. (criterion 1)

**Deferred (explicitly):**
- The provenance VIEWER (selecting a Face field to see its originating sentences with retracted/generalized markers) - storage lands here, the UI lands in Phase 8. (I8)
- The time-travel / audit command (reconstruct the Face at any sequence number and diff two reconstructions) - CUT from v1 to the Grasscatcher rather than sequenced: the append-only face_events log leaves it reconstructible at any future date, no North-Star clause needs it, and no single-project failure mode has been named that it prevents. v1 keeps only the cheap half: every Face version records the event sequence number it was derived at. (I7)
- Compile quality tuning and prompt iteration beyond convergence; v1's bar is faithful and bounded, not elegant.
- Multi-turn clarifying dialogue strategy beyond the targeted sharpening loop in Phase 5.

## Phase 5 â€” Phase 5 - Roadmap steps with immutable IDs, and a commission that is free until confirmed

Serves criterion 2. Two failures converge here: a handback landing on the wrong step because the compiler regenerated the list, and Crucible re-deriving a North Star from 'Build the backend' because commissionability was a prompt instruction rather than a predicate. Both are data-model problems, cheap now and impossible later.

**Near-term specifics:**
- Every roadmap step gets an opaque immutable ULID at creation that survives all rewrites. The compiler may only ADD, RETIRE or AMEND steps by ID - never regenerate the list. (I16, M7)
- Write-lock steps carrying a live commission against structural operations (merge, split, delete, retire), enforced in the LEDGER WRITER, not in the compiler prompt. (I17, M8)
- When John's correction genuinely requires a merge or retirement of a locked step, surface an explicit confirmation naming the affected runs and stating what happens to them. (I17, M8)
- Commissionability as a unit-tested PURE PREDICATE: a step may not be proposed for commission unless it has a named deliverable, an acceptance sentence, and at least one Face-anchored constraint carrying a provenance pointer into source_text. (I14, M2)
- Steps failing the predicate enter a `needs_sharpening` state that triggers a targeted question loop asking ONLY for the missing element, or offers an optional researchPrime commission - itself a confirmable spend, never silent. (I15, M2)
- Dry-run / estimate mode: computing skill, seat, depth and a cost/duration estimate spends nothing, so propose is genuinely free and confirm is genuinely the first spend on the commission path. (I55)
- The proposal card shows skill + seat + depth + explicit cost/duration ESTIMATE + the bound step's title and ULID, all before any spend. (I21, criterion 2)
- A commission is always proposed FOR a named roadmap step, never free-floating - enforced by the Phase-2 typed foreign key, not by convention. (criterion 2)
- Concurrency test: run refine_goal during an in-flight commission and assert the handback lands on the ORIGINALLY bound step. (M7)
- Confirmation records `who` with the identity provenance decided in Phase 1. (criterion 2, I20)

**Deferred (explicitly):**
- Automatic step ordering, dependency graphs and critical-path suggestion - v1 roadmap steps are a list with IDs.
- Auto-sharpening a vague step without confirmation, and automatic researchPrime dispatch - always an offered, confirmable spend in v1.
- Cost-estimate calibration beyond order-of-magnitude accuracy; the estimate must be honest and labelled as an estimate, not precise.
- Multi-step / batch commissions - one step, one commission in v1.

## Phase 6 â€” Phase 6 - Confirm to launch to live truth, hardened: intent, capability, lease, outbox, gates, and the build beat

Serves criteria 3 and 5. The invisible hole between 'spend authorized' and 'process exists' produces no signal at all, and kill -9 emits no event - so any event-only status design is confidently wrong exactly when John most needs it right. This phase also proves the difference between driving the trio and driving a demo, by surfacing a real HALT as a real confirmation.

**Near-term specifics:**
- Confirmation writes an INTENT record. A durable launcher, restarted at boot, reconciles intents to processes and either starts, resumes, or explicitly FAILS them with a recorded cause. On startup, a confirmed-but-unlaunched commission is never left silent. (I32, M17)
- Separate the credentials: ANCHOR_TOKEN authenticates John interactively; confirm-time mints a DISTINCT run-scoped capability - single-purpose (submit this one handback), revocable, TTL exceeding the run's budget ceiling. Test with a token deliberately expired mid-run. (I30, M18)
