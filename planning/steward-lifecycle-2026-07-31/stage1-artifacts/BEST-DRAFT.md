# Master Plan (draft)

**North Star:** A project in Anchor is stood up, planned, and driven BY TALKING TO ITS STEWARD. John describes the project in his own words; the steward compiles that description into the project's Face and Campaign Roadmap, proposes a commission for a named roadmap step, and - only on John's explicit confirmation - Anchor executes it as a real trio run. The produced plan comes back as an artifact John can read on screen and change by talking; when he says start, Foreman executes and the Roadmap shows the truth about what is running. Nothing is spent, written, or started without a human confirmation, and the campaign ledger remains the single source of truth. NON-GOALS: portfolio altitude (High Seat cross-project reporting, pause, resource conflicts) is deferred; no changes to Crucible/Foreman/researchPrime themselves; no bespoke plan template (the Crucible plan shape IS the template); no steward persona/livery, mobile/iPad; nothing that makes the steward do the planning itself rather than commission it.

**North-Star AMENDMENT A1 (explicit, recorded - not implied):** *talking / describing / correcting = TYPED CONVERSATIONAL DIALOGUE in Anchor; speech-to-text and audio input are out of scope.* A1 is appended to the non-goal list above, read back to John verbatim at the Stage-1 lock, and his confirmation recorded with `who` + timestamp in the decision log (D-D). The locked vocabulary - **typed**, never *spoken* - is used end to end below: in every success criterion, every phase, and every acceptance scenario.

## Success criteria
- Fresh start: from a project with no Face, no Strip and no roadmap, a TYPED conversational description produces a Face north-star AND at least one roadmap step, with ZERO chat turns persisted (E5: Strip receipts + roadmap events + Face narrative are the sole durable ledger; the typed dialogue COMPILES into the Face via refine_goal -> face_rewrite_receipt). The Face's own first write is itself human-confirmed.
- Propose/confirm: a commission is proposed FOR a named roadmap step (never free-floating), showing skill + seat + depth BEFORE any spend; nothing runs until John confirms, and the confirmation records `who`. Engine halves already exist: job-lifecycle.mjs proposeCommission (141) / confirmCommission (250).
- Real execution + validated handback: Anchor executes the confirmed commission as a real trio run (job_runner.py / terminal_session.py / lanes.py substrate) and returns a handback validated by receipt-validate.mjs (required: active_effort, why_next, grasscatch_why, tool_depth_why, human_wait, uncertainty_flags); a malformed handback is REFUSED, never absorbed - AND a refused or incomplete handback still leaves John something to read (raw doc-trio read-only + partial card + REFUSED banner). Refusal never means invisible spend.
- Reviewable artifact + typed refine: the produced plan renders as an artifact card (packet-view.mjs classifyArtifact/buildArtifactCard already exists) and a TYPED correction produces a new version through the SAME propose -> confirm path.
- Honest status: the Roadmap step status reflects the ACTUAL state of the Anchor session across park (STATUS_IDLE), restart and kill (Windows-native `taskkill /F`) - it never reports work that is not running. Status flows as status_flip events; the projection derives.
- Auth-ON proof: every criterion above passes with ANCHOR_TOKEN set, asserted on OUTCOMES not plumbing. This surface shipped broken twice in one week because effectively the whole Anchor suite runs auth-off.
- Single writer, proven: roadmap_events has exactly ONE writer, proven by a concurrency test (hardening law: a durability claim is a STORAGE claim - name atomic write + lock/serialization + a concurrency test) run ON THE SUBSTRATE THE BOOT PATH ALLOWS, not by prose. Anchor must not become a second writer.
- Say start -> Foreman executes: on an approved plan, a typed "start" produces a BUILD commission bound to the same roadmap step, confirmed on the same spine; Foreman runs under the same supervisor/lease/budget/halt machinery, and the Roadmap shows true wave-level state throughout, including across an Anchor restart.

Eleven phases, numbered 0-10 in ONE sequence (no inner/outer numbering), that invert the obvious build order and then immediately test that inversion. **Phase 0** is written work only: the gate inventory, the exhaustive start-path inventory, a classifyArtifact falsification run pasted verbatim, a field-by-field handback EXTRACTABILITY MATRIX measured over real on-disk trio outputs, and four decision-log entries (D-A..D-D) whose rules are locked BEFORE the measurements so consequences are downstream of evidence. **Phase 1 is the walking skeleton**: the entire motion - typed description -> Face -> named-step proposal -> confirm recording `who` -> run -> artifact on screen -> honest status - run end to end with ONLY the trio leg stubbed, early enough that its failure can still kill or reshape the spine, with four named falsifiers. **Phases 2-4** then make the skeleton physically true: the ledger substrate (SQLite WAL on the local non-synced path the boot check allows, one Node writer, a Python outbox with a full crash matrix), the confirmation choke point (single-use token bound to project/step/commission-hash/principal, idempotent CAS confirm, a two-tier confirm grammar on one spine, auth-ON as the default test mode), and a detached supervisor with lease-based liveness proven by Windows-native kill plus a zero-spend rehearsal commission. **Phase 5** proves ONE real HALT -> steward asks -> John confirms -> resume cycle against real Crucible, because HALT is the normal path and unattended completion is the special case. **Phases 6-8** build the talking surface for real (draft-Face state without transcripts, content-addressed append-only Face, a WHAT/WHY-only compile guarded by a not-planning lint AND a proposability probe, the confirm screen as its own deliverable with a runner-owned budget, provenance-tagged handback with refusal semantics and a degraded-but-reviewable path). **Phase 9** makes the Roadmap honest over a REAL Foreman run, and **Phase 10** proves all eight criteria auth-ON on outcomes before any optimization is layered on. The Phase-1 skeleton buys ordering evidence; it buys NO hardening exemptions - every gate it skips is named and owed by a later phase. Every phase serves a named criterion; every non-goal-adjacent temptation is deferred by name rather than dropped.

## Phase 0 — Stage-1 written deliverables and locked decisions (no code)

Four things that are currently assumptions would each detonate mid-build if discovered late: what the trio's halts actually say, how many ways a job can start, whether the existing classifier understands a Crucible doc-trio, and whether we are allowed to touch the trio. Serves criteria 2, 3, 4 and 7 by removing the unknowns they rest on. Costs a day of reading and grepping; buys the right to plan the rest honestly.

**Near-term specifics:**
- GATE INVENTORY table, written: one row per Crucible approval gate (Stage-0 North Star lock, Stage-1 Master Plan approval, Stage-2 Implementation Plan approval) and per Foreman blocker halt, with columns gate_id, rendered question text VERBATIM, accepted answer grammar, static-vs-dynamic, and sha256 of the rendered text. Rule stated in the table's header: anything not in this table is an unknown halt and MUST surface as awaiting_human with the raw prompt text verbatim - never guessed at, never auto-answered.
- START-PATH INVENTORY, written and exhaustive: grep the runner's entry symbol across job_runner.py, terminal_session.py, lanes.py, every Node caller, every HTTP route, and every existing UI run button. One row per path with a disposition of route-through-token | delete | hard-disable-behind-the-same-gate. An inventoried-but-open bypass counts as a hole, not as documentation.
- FALSIFY classifyArtifact NOW, not in a build wave: take a real converged Crucible doc-trio off disk (the Crucible repo's own converged plan set), run it through packet-view.mjs classifyArtifact/buildArtifactCard, and PASTE THE ACTUAL OUTPUT VERBATIM into this plan - the raw classification result and the rendered card fields, not a summary of them. That paste is an EXIT CONDITION on Phase 0: Phase 1 may not start while it is missing. Exactly two consequences are permitted: (a) the adapter emits a DOC-TRIO MANIFEST that presents as one artifact the existing classifier already understands (packaging, not a new template - honours the non-goal); or (b) HALT at an explicit NORTH-STAR AMENDMENT GATE where John is asked, in the two-tier confirm grammar, to amend the no-bespoke-plan-template non-goal. Option (b) is a gate, never a build-time choice - no wave may adopt a new plan template silently, and 'the classifier didn't like it' is not authority to write one.
- PHASE-0 DELIVERABLE - HANDBACK EXTRACTABILITY MATRIX (scheduled work, not an assumption): for each of the six required fields (active_effort, why_next, grasscatch_why, tool_depth_why, human_wait, uncertainty_flags), attempt adapter-side extraction against AT LEAST FIVE real on-disk trio outputs already present on this machine (Crucible run journals and converged doc-trios, Foreman wave journals). The deliverable is a field x run table - each cell `observed` with its source_ref, or `absent` - plus a measured absent-rate per field. This is the evidence the refusal semantics below are computed from.
- DECISION-LOG entry D-A (handback fields), with its DECISION RULE LOCKED IN ADVANCE of the measurement so refusal semantics sit DOWNSTREAM of evidence rather than upstream of it. Decision: adapter-side EXTRACTION from artifacts the trio already emits; teaching the trio to emit fields natively violates the 'no changes to Crucible/Foreman/researchPrime' non-goal and would require an amendment. Rule, applied to the matrix above: (i) measured absent-rate 0-20% on uncertainty_flags or human_wait -> absent on those two fields is a REFUSAL, as drafted; (ii) absent-rate 21-99% -> those fields move to the DEGRADED path below and refusal is reserved for structurally malformed handbacks, because refusing on a field the trio simply does not emit would turn every paid run into nothing to read; (iii) absent-rate 100% -> the field is unattainable by extraction and is either struck from the required envelope or carried to an amendment gate - decided by John at the Stage-1 lock and recorded with `who`.
- DEGRADED-BUT-REVIEWABLE PATH, specified here and built in Phase 8: a refused or incomplete handback NEVER leaves John with paid spend and nothing to read. The run surfaces (1) the raw doc-trio, read-only, exactly as it landed on disk, (2) a PARTIAL artifact card carrying observed fields ONLY, and (3) a visible REFUSED / INCOMPLETE banner naming which fields were absent and why. No synthesized field may appear on the degraded path. Refusal means 'this handback is not trusted', never 'this run is invisible'.
- DECISION-LOG entry D-B (storage substrate) - ONE SUBSTRATE STORY, stated once and binding everywhere: the authoritative ledger is SQLite in WAL mode on a LOCAL, non-synced path with real transactional guarantees, not hand-rolled file locking; any synced/OneDrive/UNC location is an EXPORT, never the source of truth, and boot REFUSES to start on one, naming the path. Consequence, enforced in Phase 2 and Phase 10: every durability gate runs ON THE SUBSTRATE THE BOOT PATH ALLOWS - the local non-synced path on the real Windows machine, not a CI container filesystem. Synced-path tests exist for exactly one purpose, to prove the boot refusal and the detection fire; a green concurrency or crash test on a synced path is NEVER a durability receipt, because the product refuses to run there.
- DECISION-LOG entry D-C (compile/plan bright line), CUT to the smallest thing that is still useful: the compile emits the Face north star and steps carrying WHAT (outcome) and WHY (rationale) - and nothing else. Size class, commissionability and depth are NOT compile outputs; they are derived at PROPOSE time and shown on the human-confirmed proposal, where a wrong judgment is visible before spend rather than baked silently into the Face. The line is held by a FALSIFIABLE NOT-PLANNING LINT in CI with an explicit forbidden-construct list (wave/phase decomposition, acceptance criteria, sequencing or dependency language, effort/size labels, tool-seat-depth naming) and a fixture corpus of passing AND failing compiled Faces, so the lint can be shown to catch a violation rather than merely asserted to exist. Every future proposed enrichment of the compile gets its own decision-log entry arguing the line.
- D-C INVERSE GUARD (the step must still be specifically proposable): a WHAT/WHY-only step is worthless if nobody can commission it. A PROPOSABILITY PROBE runs over every compiled step - the proposer must fill skill + seat + depth from the step text plus the Face ALONE, and must declare whether it had to invent plan content to do so. A step that fails the probe is NOT fixed by enriching the compile with HOW; the compile asks John a clarifying question and his answer lands as more WHAT/WHY. Probe first exercised in Phase 1 as a named falsifier, enforced in CI from Phase 6.
- DECISION-LOG entry D-D + NORTH-STAR AMENDMENT A1, recorded rather than implied: 'talking / describing / correcting = TYPED CONVERSATIONAL DIALOGUE in Anchor; speech-to-text and audio input are out of scope.' The amendment text is appended to the North Star at the head of this plan, read back to John VERBATIM at the Stage-1 lock, and his confirmation recorded with `who` and a timestamp in the decision log - the same evidence standard every other confirmation in this system carries. The locked vocabulary is then used end to end: every success criterion, phase and acceptance scenario says 'typed', never 'spoken'. Cheap now, expensive at acceptance.

**Deferred (explicitly):**
- Design of the pre-answering optimization for static gates - deliberately deferred to Phase 10, after the resume channel is proven, so it can never become the primary mechanism.
- Any source change to Crucible, Foreman, or researchPrime - blocked behind an explicit North-Star amendment per D-A.
- Portfolio-altitude gates (High Seat cross-project reporting, pause, resource conflicts) - named non-goal.
- Brownfield ingest of an existing ECGBERHT.md into a Face.

## Phase 1 — The walking skeleton: one falsifiable end-to-end talk-to-artifact run (trio leg stubbed)

The whole North Star is ONE motion - describe, compile, propose, confirm, run, read, see the truth - and every ordering argument in this plan is a bet that the motion holds together. This phase makes that bet falsifiable while it is still cheap to lose. It runs the entire spine end to end with ONLY the trio leg stubbed: typed description -> Face north star + at least one named step -> proposal bound to that named step -> confirm recording `who` -> stub run -> artifact card on screen -> honest status. Nothing else may be stubbed: the store, the single writer, the token, the confirm grammar, the ledger events and the projection are the real ones. It sits HERE, not at the end, because if the motion is wrong the remaining phases are the wrong phases - Phase 1 must be able to KILL OR RESHAPE the spine, which it cannot do if it runs after the spine is built. This is not a relabelling of a later integration wave; the later phases harden what this phase proves.

**Named falsifiers (any one reshapes the plan before Phase 2 starts):**
- The compile cannot produce a step whose skill + seat + depth a proposer can fill without inventing plan content -> the D-C bright line is drawn in the wrong place; reshape Phase 6 before building it.
- The motion costs more confirmations than the stated confirm budget -> the confirm grammar is wrong; reshape Phases 3 and 7.
- The artifact leg cannot render a real doc-trio shape at all (per Phase 0's pasted falsification output) -> the artifact leg, not the talk leg, is the live risk; pull Phase 8 earlier.
- Honest status cannot be derived at all without the supervisor -> pull lease liveness forward out of Phase 4.

**Near-term specifics:**
- REAL SUBSTRATE, REAL WRITER: the slice writes to the D-B store (local, non-synced, SQLite/WAL) through the SINGLE Node writer module, with roadmap_events, commissions, confirmations and the blob store in their Phase-2 shapes. The slice may ship WITHOUT Phase 2's durability RECEIPTS (concurrency test, crash matrix, outbox drain proofs); it may NOT ship on a different substrate, with a second writer, or on a hand-rolled file store.
- THIS SLICE DELETES NO HARDENING GATE. Every gate it skips is named here and OWED by a later phase: concurrency + crash receipts (Phase 2), per-start-path negative tests, idempotent CAS confirm and the auth-ON baseline (Phase 3), lease liveness and the never-auto-retry rule (Phase 4), the real-Crucible HALT cycle (Phase 5). No wave after Phase 2 may cite this slice as a durability receipt. If schedule pressure later proposes trading a gate for slice velocity, that is a North-Star violation on its face: the North Star requires BOTH the talk path AND the no-silent-spend law, and neither may be traded for the other.
- TRIO LEG STUB, and only that: the stub emits a REAL on-disk doc-trio shape (the same converged Crucible plan set used in Phase 0's falsification), so the artifact and handback legs meet real bytes rather than a fixture invented to pass.
- CONFIRM BUDGET, stated and MEASURED here: the full stand-up-to-artifact motion costs at most TWO spend-confirms and at most FIVE gate-confirms. The slice reports its actual counts in the wave receipt; exceeding the budget is a falsifier, not a footnote.

'Nothing is written without a human confirmation' includes the Face's own first write.

## Phase 2 — The ledger spine: one writer, made physically true

Criterion 7 is a STORAGE claim, and the hardening law says a durability claim must name its atomic write, name its lock/serialization mechanism, and ship a concurrency test. Everything downstream (status truth, confirmations, halt records, chain reconstruction) writes here, so a second writer or a lost event corrupts every other criterion silently. Built before any feature that would want to write.

**Near-term specifics:**
- SQLite in WAL mode at a LOCAL, non-synced path (e.g. under %LOCALAPPDATA%), holding roadmap_events, commissions, confirmations, halt records, leases, and the content-addressed blob store.
- Boot precondition check: detect a synced/replicated/UNC/OneDrive store location and HALT with a clear message naming the path and the supported alternative. Path support is a precondition, not a warning - never corrupt quietly.
- roadmap_events schema with a monotonic per-run sequence enforced as UNIQUE(run_id, seq) in the store, plus a chain_id column present on every event from day one.
- Exactly ONE Node writer module holds the write credential to roadmap_events. The Python execution side (job_runner.py / terminal_session.py / lanes.py) gets NO write credential at all - it appends status changes to an OUTBOX IT OWNS (its own SQLite file; one transaction per append; monotonic outbox_seq; content hash; a stable outbox_id); the single Node writer drains that outbox and emits ordered roadmap_events. Enforced by credential/permission, not convention, with a test asserting a Python-side direct write to roadmap_events FAILS.
- OUTBOX ATOMICITY AND CRASH COVERAGE - the drain is the seam most likely to lie, so it is tested as such. The drain is AT-LEAST-ONCE with idempotent dedupe on UNIQUE(outbox_id) in roadmap_events, so a redelivered record can never become a second event. Crash matrix, all four cases required: kill Python mid-append; kill Node mid-drain; kill Node AFTER the roadmap_events commit but BEFORE the outbox acknowledgement; kill both together - each asserting no lost event, no duplicate event, no torn record, and no gap in the roadmap_events sequence.
- HONEST SSOT BOUND, stated rather than claimed away: roadmap_events is the single source of truth, but between a Python append and a completed drain the ledger LAGS by a bounded interval. The projection therefore renders 'as of seq N', derives liveness from the lease (Phase 4) and never from the outbox, and no surface may present un-drained outbox content as live status. The bound is measured in this phase and recorded in the wave receipt.
- Hardening-law receipt written into the wave's acceptance criteria: atomic write = single WAL transaction commit; serialization = single-writer process + UNIQUE(run_id, seq) compare-and-append; concurrency test = N racing writers asserting one writer, strictly ordered sequence, and zero lost events. The claim is the test, not the prose.
- Read-side EVENT-ORDER INVARIANT: any projection encountering a non-monotonic sequence or an illegal transition (complete before running, running after lost) RAISES rather than rendering a plausible-but-wrong Roadmap.
- REAL-SUBSTRATE GATE, per D-B's one substrate story: the concurrency and crash tests are a required gate ON THE SUBSTRATE THE BOOT PATH ALLOWS - the local non-synced path, on the real Windows machine, with real WAL and real Windows file locking. A CI container run is a fast pre-check only, never the receipt, because a green test on a substrate the product does not run on is a false receipt. Separately and for a DIFFERENT purpose, a synced-path test asserts the boot REFUSAL fires and names the path; that is a detect/refuse proof and is explicitly NOT a durability receipt.
- Crash test uses the Windows-native kill (`taskkill /F /PID <pid>` - no graceful-shutdown path, no cooperative signal): kill the writer mid-transaction, restart, assert no torn event and no gap in the sequence.

**Deferred (explicitly):**
- Export/publish of the ledger to a synced folder for off-machine reading - the export writer is a later, read-only-derived concern.
- Multi-machine or multi-host replication.
- Cross-project ledger tables (portfolio altitude is a non-goal).

## Phase 3 — The confirmation choke point and auth-ON baseline

Criterion 2 and the 'nothing is spent, written or started without a human confirmation' clause of the North Star cannot be enforced by discipline at N call sites. Move the guarantee to the single point every run must pass through, then close every path that bypasses it. Criterion 6 rides along here because this surface shipped broken twice in one week with auth effectively off - so auth-ON becomes the baseline test mode starting at the first wave that has an endpoint.

**Near-term specifics:**
- Confirmation token bound to (project_id, step_id, commission_hash, principal), single-use, minted ONLY by confirmCommission (job-lifecycle.mjs:250) off a proposal from proposeCommission (job-lifecycle.mjs:141). No job enters the runner without a valid, unconsumed token - rejected by construction, not by an if-check at the top of a function.
- Negative test PER START PATH from the Phase-0 inventory, each asserting an unconfirmed start is refused. Paths that cannot be routed through the token check are DELETED or hard-disabled behind the same gate in this phase - not documented and left open.
- Per-principal tokens (`john` vs `service`). Every confirmation records resolved principal, token id, and issuance time. A service principal may NOT confirm spend - rejected outright, with a test.
- TWO-TIER CONFIRM GRAMMAR OVER ONE SPINE: `spend-confirm` (money and agents start: a commission, a re-confirm after a budget breach, a re-commission of a `lost` step, the Foreman start) and `gate-confirm` (no new spend, a decision a waiting run needs: the Face first write, a Crucible approval-gate answer, a correction accepted into a re-proposal). The tiers differ ONLY in what they render - a spend-confirm additionally requires an explicit ceiling echo - and never in their machinery: one code path, one `who` recording, one ledger event shape, one CAS idempotency mechanism. Two tiers of prompt, never two confirmation systems. A service principal may issue NEITHER tier.
- CONFIRM-COUNT BUDGET, treated as a design constraint rather than discovered later as an annoyance: a full stand-up-to-artifact motion costs at most TWO spend-confirms and at most FIVE gate-confirms (Face first write + Crucible's three approval gates + one spare). Measured in Phase 1, re-measured in the Phase 10 acceptance sweep; exceeding it is a design defect that reshapes this phase, not a UX note. The budget may never be met by removing a confirmation the North Star requires.
- IDEMPOTENT CONFIRM by construction, for BOTH tiers: the proposal (or open gate) mints a single-use confirmation id; confirm is a compare-and-swap that consumes it, so a duplicate call returns the FIRST call's result rather than starting anything. Tested the three ways it really happens - concurrent duplicate confirms, a confirm replayed after reconnect, and a confirm whose response was lost.
- At most ONE IN-FLIGHT RUN PER STEP enforced as a uniqueness constraint in the store (partial unique index), not as application logic.
- Typed-allowlist argv builder for the Anchor->trio adapter with NO free-form passthrough string, plus a test asserting the constructed argv can never contain --yes / --auto-approve / -y for any input, including adversarial ones. Auto-approval is made structurally impossible, not discouraged.
- Auth checked on the STREAM, not only the handshake: token checks asserted on SSE/WebSocket frames, artifact fetch, and event/projection reads. No token in a query string (it leaks into logs).
- ANCHOR_TOKEN-set is the DEFAULT test mode for this surface from here on; any test that passes only with auth off FAILS the wave. Auth-off is the special case.
- Conversation bound to a project id at creation and immutable: a conversation with no project id can ONLY do project selection or new-project stand-up. Every write (Face compile, commission, ledger entry) asserts the target project id matches the conversation's and refuses on mismatch. The bound project renders persistently in the dialogue surface - always visible, never inferred.

**Deferred (explicitly):**
- Principals beyond john|service; roles, multi-user, token rotation UI, OAuth.
- Rate limiting and abuse controls (single-human system).
- Re-binding a conversation to a different project - immutability is the point.

## Phase 4 — Detached supervisor, lease liveness, and the zero-spend rehearsal

Criterion 5 says status must reflect the ACTUAL state. A stored status string cannot know its process died. This phase makes liveness the source of truth and makes the UI a viewer that never owns a run - which is also what lets Phase 5's HALT cycle survive an Anchor restart. The rehearsal commission is the leverage: it exercises the entire path at near-zero cost, continuously, from here to the end of the build.

**Near-term specifics:**
- Confirm ENQUEUES a durable job record and returns immediately. A supervisor process owns execution, survives Anchor restarts, and reconstructs all run state from the store on reattach. The UI is a viewer, never an owner.
- LEASE-BASED LIVENESS: a run is `running` only while its lease is fresh (tens of seconds, not hours). The run process renews a heartbeat; a REAPER - not the corpse - flips an expired run to `lost`.
- Three non-running states kept honestly distinct: `awaiting_human` (a halt record is open), `lost` (lease expired), `failed` (terminal error) - all distinct from `complete`. A run blocked on a gate must NEVER render as `running`.
- Acceptance criterion (on the wave, not in a code comment): the UI never renders `running` from a stored status alone - it renders from lease freshness.
- Liveness tested by the WINDOWS-NATIVE KILL, named explicitly because POSIX SIGKILL does not exist here: `taskkill /F /T /PID <pid>` against the run's process tree, plus TerminateJobObject on the run's Windows JOB OBJECT (the same job object the budget primitive in Phase 7 owns) - no graceful shutdown path, no cooperative signal, no atexit hook that could tidy up the lease on the way out. Assert the Roadmap reaches `lost` within the expiry window. Machine-reboot and OOM variants included.
- The three real detachment cases tested explicitly - browser disconnect, Anchor restart mid-run, machine reboot - each asserted to end in a truthful state (still running and reattachable, or `lost`).
- A `lost` step is RE-COMMISSIONABLE: reaping releases the one-in-flight-per-step constraint. Full loop tested: kill -> lost -> re-propose -> confirm -> run.
- NEVER-AUTO-RETRY rule: a `lost` or failed run is never restarted without a fresh human confirmation, however obviously transient the cause. Automatic recovery would spend without confirmation.
- REHEARSAL COMMISSION (no-spend dry run): a proposal executable against a trio STUB that exercises the whole path - token, supervisor, halt record, handback validation, artifact card, ledger events - with zero spend. Runs in CI from this phase onward so wiring stays proven.

**Deferred (explicitly):**
- Supervisor as an installed Windows service with autostart - manual launch is acceptable for now.
- Cross-machine supervision.
- Tuning of lease expiry against real long-run latency - a fixed short expiry now, calibrated later against real trio runs.

## Phase 5 — HALT-first: one real halt -> ask -> confirm -> resume cycle against real Crucible

The premortem's single largest inversion: treat HALT as the NORMAL path and unattended completion as the special case. Crucible has three you-approve gates by design, so a plan built on 'it will usually just finish' is built on the rare case. This wave must go GREEN on one OBSERVED real cycle against real Crucible before any wave depends on unattended completion. Serves criteria 2, 3 and 5.

**Near-term specifics:**
- Durable HALT RECORD as the spine of execution: whenever the trio blocks on a gate, the supervisor writes {run_id, gate_id, rendered_question, answer_grammar, resume_token, face_hash, opened_at} to the store. Nothing about a waiting run lives only in a process's memory or a terminal buffer.
- A gate answer IS a micro-commission: gate answers route through the SAME propose->confirm path as commissions, as the `gate-confirm` tier of the Phase-3 grammar. One confirmation code path, one `who` recording, one idempotency mechanism, one ledger event shape for every human decision in the system.
- Resume via Crucible's OWN checkpoint/resume (the engine already halts and resumes at user gates): the supervisor records the answer, then relaunches with --resume. A live-stdin bridge is a FALLBACK only, permitted only if resume is measured to be lossy - measure it in this wave and record the result.
- Gate satisfaction requires a SIGNED CONFIRMATION RECORD carrying real principal + gate_id + face_hash. Negative test: a run with ZERO confirmation records cannot reach Stage-2 output.
- Every gate PASSAGE recorded as a first-class ledger event, so an auto-passed or skipped gate is visibly ABSENT from the chain rather than indistinguishable from an approved one.
- Unknown halt handling: any halt whose rendered text does not match the Phase-0 gate inventory surfaces as `awaiting_human` with the raw prompt text VERBATIM - never paraphrased, never guessed.
- GREEN condition for this phase: one real end-to-end cycle observed against real Crucible - it halts, the steward asks, John confirms, the run resumes and reaches the next gate - with the halt record, confirmation, and both gate events present in the ledger.

**Deferred (explicitly):**
- Pre-answering of static gates - deliberately deferred to Phase 10 as an optimization layered ON TOP of this channel, never as a substitute.
- Concurrent multi-run halt handling (one run at a time until the single-run cycle is proven).

## Phase 6 — Talking into a Face: draft framing state, content-addressed Face, compile lint

Criterion 1 in full: a TYPED conversational description produces a Face north star and at least one roadmap step with ZERO chat turns persisted. The trap is that a framing dialogue must survive a reconnect - so persist the ACCUMULATED FRAMING (structured state), not the transcript. The Face being content-addressed and append-only is what lets every downstream commission name the exact Face it was confirmed against. Phase 1 proved this motion end to end; this phase makes it real and lints it.

**Near-term specifics:**
- Structured, append-only DRAFT-FACE document with a stable draft id; exactly one immutable revision committed per turn. This is state, not transcript, and does not violate the zero-chat-turns criterion.
- Reconnect resumes framing: loading the draft id re-renders 'here is what I have so far; keep going.' Test = kill the Anchor process mid-framing, restart, resume, assert the draft is BYTE-IDENTICAL.
- ZERO-CHAT-PERSISTENCE PROOF: after a full stand-up, an automated check scans the store - every table, file, and blob - for any persisted dialogue turn and FAILS if one exists. Criterion 1's hardest clause gets a test, not an assurance.
- Face is CONTENT-ADDRESSED and append-only: every compile writes a new immutable version with a hash; the 'current Face' is a pointer. Every commission records the exact Face hash it was confirmed against; the artifact viewer can always resolve that hash.
- Test that MUTATING a prior Face version is impossible - write-protected at the store level, not merely logged.
- face_rewrite_receipt DERIVED as a diff between two immutable Face versions, rather than trusting a narrative the compiler wrote about itself.
- COMPILE DETERMINISM RECEIPT on every face_rewrite_receipt: draft revision hash, model, prompt version - so a re-compile that diverges is visibly a different compile rather than an unexplained different Face.
- FACE FIRST-WRITE CONFIRMATION SURFACE (the one named in Phase 1, built for real here): `compile preview -> CONFIRM WRITE`. The compiled Face north star and step list render as a preview that is NOT persisted; the write lands only on a `gate-confirm` that echoes the north-star text back and records `who`. A compile that writes before that confirm is a no-silent-write violation, tested negatively.
- NOT-PLANNING LINT over compiled Faces, run in CI (per decision D-C), and FALSIFIABLE rather than merely declared: the compile emits the Face north star plus steps carrying WHAT (outcome) and WHY (rationale) and nothing else. Explicit forbidden-construct list - wave/phase decomposition, acceptance criteria, sequencing or dependency language, effort/size labels, tool-seat-depth naming - and a fixture corpus of passing AND failing compiled Faces, so the lint is proven to catch a violation rather than assumed to.
- SIZE CLASS AND COMMISSIONABILITY ARE NOT COMPILE OUTPUTS (D-C, cut deliberately): both are derived at PROPOSE time and shown on the human-confirmed proposal in Phase 7, where a wrong judgment is visible before spend instead of baked silently into the Face. The compile never labels a step's size and never marks a step non-commissionable.
- PROPOSABILITY PROBE in CI (the D-C inverse guard): for every compiled step, the proposer must fill skill + seat + depth from the step text plus the Face ALONE, and must declare whether it had to invent plan content. A step that fails is NOT repaired by enriching the compile with HOW - the compile asks John a clarifying question and his typed answer lands as more WHAT/WHY. Failing the probe blocks the wave.

**Deferred (explicitly):**
- Speech-to-text / audio input - explicitly out of scope per the Phase-0 North Star amendment.
- Brownfield compile from an existing repo or ECGBERHT.md.
- Cross-project Face or portfolio narrative (High Seat is a non-goal).
- Steward persona/livery.

## Phase 7 — The confirm surface as the primary deliverable

Criterion 2 is only real if John can tell what he is approving. A confirm prompt that buries the bound step produces confidently-wrong commissions that pass every technical check. This phase treats the one screen as the deliverable and adds the budget ceiling the runner actually enforces - because a ceiling the trio polices itself is not a ceiling.

**Near-term specifics:**
- A commission is proposed FOR a named roadmap step, never free-floating, showing skill + seat + depth BEFORE any spend - all three DERIVED HERE, at propose time, not read off the Face (D-C). The derivation shows its inputs, so a wrong seat or depth is visible and correctable in the same turn.
- SIZE CLASS derived at propose time and rendered on the proposal as part of the ceiling, since the compile no longer carries it. The class is a promise the runner keeps, not a label the compiler guessed.
- The BOUND STEP is the most prominent element of the confirm prompt: step id, exact name, position in the roadmap, current status - and the confirmation must ECHO THE STEP ID back.
- One screen answering four questions: WHAT step, WHAT will run, WHAT it may cost as a hard ceiling, WHAT will change on disk. Acceptance test: John can correctly answer all four from the prompt alone, tested with a real proposal, before this wave is called GREEN.
- Below-threshold or near-tie step matching REFUSES to propose and asks a disambiguating question instead. Refusing to propose is always cheaper than a confirmed wrong commission.
- Match CANDIDATES AND SCORES logged on the proposal itself, so a mis-bind is auditable after the fact rather than indistinguishable from a correct bind.
- REAL BUDGET IN THE RUNNER, with the ENFORCEMENT PRIMITIVE NAMED: the supervisor launches the trio inside a Windows JOB OBJECT it owns, so wall-clock and process limits are enforced by the OS and cannot be talked out of by the child; token and agent-count ceilings are polled from the trio's own run journal at each heartbeat. On breach the supervisor SUSPENDS the job object (suspend, not terminate - the run must remain resumable), writes a halt record with gate_id=`budget_breach` carrying used-vs-ceiling, and surfaces a re-confirmation turn ('used X of Y; continue?') through the Phase-5 channel. Never silent continuation, and never a ceiling the trio polices itself.
- POST-HALT RESUME STORY, stated end to end: on a `spend-confirm` of a raised ceiling, the supervisor resumes the SUSPENDED job object in place; if the process tree is already gone, it relaunches via Crucible's own `--resume` from the last checkpoint - never a fresh run silently re-billed as a continuation. If Phase 5's measurement showed resume to be lossy, the re-confirm prompt SAYS SO, with what will be re-done, before John pays for it. On decline: the job object is terminated, the run ends `failed`, and whatever partial work exists is still surfaced through the degraded-but-reviewable path - a declined continuation is not an invisible run.
- Cost presented at confirm time as an explicit CEILING with a stated worst case, not a point estimate. Confirmed-ceiling vs actual reconciled in the ledger every run so drift is visible over time.
- Re-confirmation exceeding the step's size class is REQUIRED - the class is a promise the runner keeps, not a label.
- On RE-confirmation, 'show me what changed since the last proposal' - a diff of the PROPOSAL itself, not just of the plan.
- GRASSCATCHER wired into correction turns: a TYPED correction out of scope for the bound step is grasscatched with grasscatch_why recorded, rather than silently widening the commission.

**Deferred (explicitly):**
- Learned cost forecasting from run history - fixed size classes and stated worst cases for now.
- Batch or multi-step commissions.
- Resource conflicts and cross-project scheduling (High Seat, non-goal).

## Phase 8 — Validated handback, provenance, and the reviewable artifact

Criteria 3 and 4. The failure mode is an adapter that quietly manufactures plausible field values, producing a receipt that validates and means nothing. Provenance plus outright synthesis bans on the two fields that matter, plus a degeneracy canary, make a useless signal visible rather than comfortable.

**Near-term specifics:**
- receipt-validate.mjs enforces the envelope: active_effort, why_next, grasscatch_why, tool_depth_why, human_wait, uncertainty_flags. A malformed handback is REFUSED, never absorbed.
- Every handback field carries PROVENANCE: {value, provenance: observed|synthesized|absent, source_ref}. The validator checks the envelope; a SEPARATE provenance rule decides refusal.
- Synthesis FORBIDDEN outright for uncertainty_flags and human_wait - absent-or-observed only. Whether absent on those two fields REFUSES is set by D-A's locked rule against the Phase-0 extractability matrix, not re-argued here: 0-20% measured absent-rate -> refusal; 21-99% -> the degraded path below; 100% -> struck or amended at the Stage-1 lock. grasscatch_why and tool_depth_why may be synthesized only with an explicit `synthesized` tag that renders VISIBLY in the ledger.
- DEGRADED-BUT-REVIEWABLE PATH BUILT HERE (Phase 0 specified it): a refused or incomplete handback still renders (1) the raw doc-trio read-only, exactly as it landed on disk, (2) a PARTIAL artifact card carrying observed fields only, and (3) a REFUSED / INCOMPLETE banner naming the absent fields. No synthesized value may appear on this path, and no path exists by which paid spend produces nothing on screen. Tested by injecting a handback missing each required field in turn.
- EXTRACT, DO NOT INVENT (per decision D-A): derive fields from artifacts Crucible/Foreman ALREADY emit - run journals, HALT records, budget reconciliation, convergence rounds. If the artifact does not contain the fact, the field is absent; the adapter never fills a gap.
- Raw trio output stored as a CONTENT-ADDRESSED BLOB beside the handback, so any field is re-derivable and any provenance claim is checkable.
- DEGENERACY CANARY at the ledger level: if N consecutive handbacks carry identical values for a field, flag the adapter as degenerate on the Roadmap and in the Strip. A silently-useless signal is worse than a missing one.
- Artifact card via packet-view.mjs classifyArtifact/buildArtifactCard - or the DOC-TRIO MANIFEST if Phase 0's pasted falsification output showed classification fails. The manifest is packaging, not a new template; it honours the no-bespoke-plan-template non-goal. A bespoke plan template remains reachable ONLY through Phase 0's explicit North-Star amendment gate, never as a build-time fallback chosen inside this wave.
- VERSION RELATIONSHIP as a first-class artifact: a re-commission carries the prior plan as an explicit INPUT plus the correction as a SCOPED INSTRUCTION, and the handback must include a changed/unchanged accounting keyed to stable wave/section ids.
- New plan version renders AS A DELTA against its parent by default, with the full document one click away.
- HONEST LIMIT at correction time: if Crucible cannot honour 'change only this' without a trio change (non-goal), the confirm prompt says 'this will regenerate the whole plan' rather than presenting a full regeneration as a targeted edit.
- A TYPED correction produces a new version through the SAME propose -> confirm path - no separate edit route.

**Deferred (explicitly):**
