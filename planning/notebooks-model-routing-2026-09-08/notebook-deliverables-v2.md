# Plan B v2 - built-in, portable Jupyter work products

Revised after Grok review 1. Plan only. First delivery is Jupyter, not other Python/R runners or IDEs. Kernels must execute on the computer running that installation's Anchor service: PUTER here, the collaborator's own host elsewhere.

## B1. The surface and durable contract

An illustrative Python/R output appears once in Deliverables and under its producing Plan step. It offers **Open notebook - runs on <Anchor host>** and **View/download source**. Files uses the same resolver. With missing host setup, show **Set up notebooks** plus source access, not a fake live button. A transient outage shows the configured host plus recovery status. Opening and registering do not execute code; running cells remains the user's action.

DELIVERABLES.md remains the sole campaign register, using the existing What | Where | Date | Step shape. Where stays a contained, backticked relative path to the authoritative .py/.R source or an existing .ipynb. Step uses the current parser's step number/name convention, not an unsupported opaque ID. Preserve existing labels/dates and the integrated-report ordering. Ordinary repository scripts are not bulk-imported as deliverables.

For a converted source `examples/demo.py`, store a versioned companion association at `examples/demo.py.anchor-notebook.json`, adjacent to the artifacts. Proposed fields: schema version, source relative path and digest, selected notebook relative path, conversion version and original notebook digest. No host URL, username, token or absolute path. This is artifact provenance, not another deliverables register. Existing .ipynb rows need no association. Parsed notebook actions are derived from the register + files + companion; they survive restart and import. Unknown or malformed companion versions leave source access and a repair status.

All three consumers (shared.js delivRow, openProducedFile and the actual Files click handler identified during implementation) call one authenticated resolver. Return typed actions/status; do not derive live capability from extension alone or silently download when Open notebook was requested. The resolver rechecks current configured host, root and paths and returns a stable Anchor launch URL containing only project/effort/artifact identity. No arbitrary live-URL allowlist or frontend-built localhost endpoint. Existing report, HTML and ordinary download actions remain unchanged.

## B2. Production completion and loss-free conversion

Affected Anchor/Steward/Trio/Foundry producer flows use one installed helper contract: persist the produced source/notebook in the MAIN project, validate it, update the association and register idempotently, then mark the producing human-facing step complete. Extend the existing scoped document-persistence path to capture notebooks, source and companion before worktree cleanup; do not assume its current document allowlist includes them. Never register a temporary worktree path as a final product. Keep unrelated user changes unstaged.

This is a recoverable ordered operation, not a claimed transaction across unrelated files. Use per-artifact/effort locking, atomic file replacement and a small pending-operation record in deployment runtime state. On interruption, recover/reconcile against the final files; incomplete artifacts remain visible as source/pending, and the step stays pending. Repeating completion must not duplicate rows. Only instructional steps requiring a notebook use this completeness gate; ordinary report-producing steps are unaffected. An unconfigured host may receive a registered portable notebook file, labeled not launch-configured, but cannot count as verified live execution.

Existing .ipynb opens without overwrite. Explicit instructional .py/.R outputs convert once to a sibling notebook (python3/ir); no pedagogical line-count cutoff. There is one technical input cap for v1: 1 MiB UTF-8 source, counted in bytes before parsing; oversized or undecodable inputs retain source access and a precise message. Preserve code as one cell, without execution, imports, cell-marker splitting, markdown inference or dependency install. Validate nbformat and kernel metadata.

Create files exclusively and atomically; never overwrite an existing sibling on a filename guess. Matching provenance permits reuse; an unrelated sibling requires explicit association or a new unique revision. A changed source shows source changed, but opens the user's existing notebook unchanged. Explicit regeneration produces a new notebook revision and changes the association only after validation/persistence. Preserve edits in both source and notebook. New notebook/source/companion files join the existing artifact persistence policy; no blanket git add or automatic promotion of unrelated files. Notebook save/output state is not a promise that code was executed successfully on this host.

## B3. Chosen remote launch/auth architecture

Use **separate Jupyter-origin cookie/password authentication**. Anchor validates the project/artifact, then redirects to the deployment-configured HTTPS Jupyter base URL plus the safely encoded `/lab/tree/<relative path>`, preserving any base-path prefix. The destination contains a file path but no credential. Anchor login does not grant or replace Jupyter login. Do not build an Anchor HTTP/WebSocket reverse proxy in v1.

Generic setup enrolls a Jupyter password or supported login credential using its documented flow; secret values never enter registers, plan files or new launch URLs. Sign in when required, not 'once forever': cookie expiry/new browser/reboot recovery must have a tested path back to the requested notebook. Existing token-bearing classroom pages remain a temporary private fallback; do not ship them. Require HTTPS, working WSS, Jupyter XSRF/origin checks and correct trusted-proxy configuration. No wildcard CORS or browser-facing localhost. Tests must assert the exact active notebook despite restored workspaces; don't reset the user's workspace to make a test pass.

First implementation proof, before converters: use a synthetic notebook on the chosen Jupyter origin to demonstrate fresh browser login, intended deep link, connected local Python/R kernels, save/reopen, session renewal and service restart. Run through the actual iPad Safari/tailnet path for the remote claim; if unavailable, label that acceptance pending. No converter effort should hide a failed launch architecture. Sources: Jupyter Server security, JupyterLab URLs and IRkernel instructions in source-notes.md. No live execution or auth changes were made during this planning task.

## B4. Built-in host setup and lifecycle

Ship reusable notebook setup/doctor support and dependency detection for JupyterLab, Python and R/IRkernel. Collaborators supply their own installations/accounts and explicitly authorize setup/install; a deliverable click never installs packages. Configure a deployment-local approved workspace root, local process/service identity, loopback port, external HTTPS base URL, service account and kernel environment. A root may contain multiple trusted projects. Other roots require explicit additional registration. No literal PUTER, Econ 588, C:/dev or John's login in product defaults or shipped skills.

Use a dedicated persistent Jupyter service/task adapter, not preview_server's ephemeral process lifecycle. Reuse proven low-level port/ownership helpers only where their contract fits. Windows is the first proven host platform; publish the tested platform/version matrix and report unsupported lifecycle platforms honestly. The adapter provides install/start/stop/status/on-boot recovery, one start lock per registration, bounded readiness/health, log redaction, ownership verification and safe cleanup of its own children. It must never take Anchor's service port or kill/adopt a process from a port/PID alone. Preserve the current manually started class service until its owner and a coordinated handover are established. Idle kernels are not blindly reaped as previews.

Run under a deliberately selected non-admin account with only needed file permissions and a minimal environment that excludes Anchor/model credentials. Setup explains that Jupyter code has that account's permissions: root_dir is not an OS sandbox and the product is not multi-user tenant isolation. Sharing the software is not granting collaborators access to John's service or filesystem. Anchor path checks enforce allowed artifact paths, but a signed-in Jupyter user can access its configured trusted root; do not pretend Anchor project authorization constrains arbitrary notebook code.

Prove both local kernel specs resolve trusted local executables and no remote Gateway/kernel manager is active. Then a harmless Python and R probe reports the host identity and uses a synthetic workspace file. Merely reaching a local Jupyter HTTP endpoint or seeing `ir` listed does not prove same-host R execution. R setup must be visible to the actual service account. Reject path traversal, drive/UNC/alternate-stream paths and junction escapes; revalidate canonical paths under locking before create/open, with server-account permissions preventing untrusted root mutation. Missing kernels, expired login, dead service and unreachable WSS have distinct actionable states.

## B5. Distribution, acceptance and rollback

Package Anchor's resolver, API/UI integration, converter/provenance, producer helper, setup/doctor and lifecycle adapter. Package compatible generic registration instructions/helper calls with all affected distributed skills through the formal Foundry improvement cycle. Installed helpers resolve package locations, never this session's absolute imports. Without Anchor running, a standalone skill still emits portable relative artifacts/register/companions; after importing/registering that project in Anchor and setting up a local host, the same notebook opens. No off-host execution is silently substituted.

Release checklist: synthetic Python/R sources and existing notebooks on all three real UI surfaces; exact target/kernel; source/notebook collisions and changes; reload; concurrent completion; crash/recovery; MAIN persistence after worktree teardown; invalid/oversized input; traversal; non-notebook regressions; host setup missing; fresh auth/renewal; connected WSS; same-host execution/save; service recovery and agreed on-boot restart. Private Econ 588 is a local acceptance case only. Actual iPad proof is separate from tablet emulation.

Install actual release archives in a clean Windows profile without John's files/settings, using synthetic fixtures only; exercise setup and an outside-Anchor skill output imported into Anchor. Build release archives from explicit source allowlists. Inspect content and paths to exclude private teaching data, notebooks, project materials, settings, journals/transcripts, logs, screenshots and credentials; also secret-scan. Verify no absolute development import paths. Public synthetic fixtures are deliberately named and reviewed, not selected by a broad notebook glob. Version-check Anchor/helper/skill contract compatibility and show upgrade guidance rather than a dead link.

Rollout: prove generic setup/auth; register/persist/convert + shared surface integration; formal producer instructions/helpers; local acceptance; clean-install acceptance; release. Back up registers and companions and retain working old class links until replacement passes. Rollback never deletes source/notebooks or kills unrelated sessions; restoring old UI leaves portable files accessible. Coordinate any restart, and do not publish or modify collaborators' systems under this planning request.

Needed because links alone do not ensure durable, discoverable host-executed work products; the producer/persistence and clean-install gates prove what the user sees. Cut: other runners/IDEs, automatic per-project lab creation, a new reverse proxy, multi-user hosting, Rmd conversion, cell splitting, silent installs and automatic execution on open.
