# Plan B v1 - Python/R notebook work products running on PUTER

Planning draft for Grok review. John's minimum: Jupyter notebooks hosted and executed by the same computer as Anchor. Other Python/R execution modes are deferred.

## User-visible result

An illustrative Python or R output is a visible Anchor work product. Its Deliverables row and producing Plan step offer **Open notebook - runs on PUTER**, plus source view/download. Files uses the same resolver. Opening never executes cells. In JupyterLab the user runs, edits and saves on PUTER; an iPad only supplies a browser. Existing notebooks open directly.

Ship this as built-in Anchor and skill behavior for collaborators too. PUTER means the computer hosting John's Anchor; on another installation it means that installation's Anchor host, never John's hostname or course path. Deployment setup registers a host-local Jupyter workspace root and its browser-reachable endpoint; Anchor projects within that approved root use the feature. Additional roots require the same explicit registration. Unsupported/unconfigured projects keep source access and offer setup, not a misleading notebook button. Econ 588 is only the private local acceptance case; clean-install tests use synthetic Python/R examples.

## Registration and source ownership

Keep DELIVERABLES.md (What | Where | Date | Step) as the campaign's sole deliverable register. Add typed notebook metadata to its parsed API response rather than a parallel deliverables database. One logical row per teaching example; source and notebook are companion actions, not duplicate rows. Identity is project + effort-relative source/notebook path, with Step tying it to its producer. Ordinary files remain files, not automatically deliverables.

Steward and Anchor production completion must register explicitly requested Python/R work products and attach them to the producing step in the same completed operation. Missing registration means the human-facing step is not complete. Reconcile/backfill already produced classroom artifacts with a preview, preserve existing row labels and dates, and do not scan/import arbitrary repository scripts. The existing Week 1/2 notebook launches remain available until replacement is verified.

Use one authenticated resolver for Deliverables, Plan-produced files and Files. Its typed response includes language, source/notebook relative paths, host label, kernel, launch URL and status. Frontends do not construct arbitrary service URLs. Existing report/artifact/file links keep their behavior; adding notebook support does not whitelist arbitrary localhost URLs.

## Scripts become notebooks safely

- Existing .ipynb is the authoritative notebook: validate and open it without conversion or overwrite.
- Explicit classroom work-product .py/.R scripts generate a sibling .ipynb once, using python3/ir kernel metadata. For these registered instructional outputs no length cutoff is necessary. Arbitrary file-list scripts require an explicit Open as notebook action; file length alone never proves teaching intent.
- Preserve code verbatim as a single cell in v1; no execution/import, dependency installation, inferred markdown, Rmd conversion or fragile source-to-cells parser. A small provenance record associates source relative path/digest, converter version and notebook digest. Enforce a bounded file size with a clear source-access fallback.
- Never overwrite an existing sibling notebook merely because the names match; reuse only with matching provenance or an explicit association. On source changes, show source changed; opening retains the existing notebook. Explicit regeneration writes a new notebook revision and updates the logical row only after it is valid. Hand-edited notebook changes survive. Use atomic create/association and per-artifact locking so double-clicks cannot overwrite or duplicate registrations.
- New notebook files and derived metadata are committed/registered only after validation succeeds. Interrupted operations leave recoverable source access, not a falsely complete deliverable.

## PUTER hosting and remote launch

Reuse supported Jupyter/Python/R installations rather than build another execution platform. Provide generic capability detection and a documented/setup-assisted install path for JupyterLab, Python and IRkernel on the Anchor host; dependency installation requires explicit setup, never a deliverable click. Setup records the approved workspace root, host service identity, loopback port and remotely reachable HTTPS endpoint in deployment-local state, not distributable skill files. A root can contain multiple Anchor projects; additional roots use separately owned registrations. Validate local process ownership to establish that compute really runs on the Anchor host, not an arbitrary external Jupyter URL. Identify the current hand-started server before coordinated handover; never adopt or kill by port/PID alone. Define an on-boot service/task under an intended non-admin account, explicit environment, bounded readiness and recovery, and actionable health errors. Jupyter never takes Anchor's service port. The implementation must use the existing supported host-service/preview mechanisms where possible, not a parallel process manager.

Choose direct Jupyter-origin browser authentication for v1, with a one-time Jupyter sign-in if required. Reuse Jupyter's supported HTTP/WebSocket auth rather than implement a new Anchor reverse proxy. Stable Anchor launch links contain only project/artifact identity, not a Jupyter bearer token. The server resolves the configured tailnet host/port and safely encoded notebook path. No browser-facing localhost addresses, wildcard CORS, public exposure or bearer tokens in new deliverables/logs. First-use sign-in is acknowledged; authenticated later clicks open the target notebook. Exact authentication setup and sign-in-to-target restoration must be proven before rollout.

Authenticate Anchor launch requests; resolve project membership and canonical real paths against the approved root; reject traversal, drive/UNC paths, alternate streams, junction escapes and unconfigured redirect hosts. Recheck on create/open to avoid symlink races. Jupyter root containment is not an OS sandbox: execution is trusted personal classroom code under the service account, not a safe multi-user/untrusted-code offering. Use least privilege and no inherited Anchor/model secrets. Missing kernel or network access is shown per language with source fallback.

## Acceptance and rollout

Fixtures cover existing notebooks, registered .py/.R, unknown sibling collisions, edited source/notebooks, Unicode paths, concurrent opens and interrupted registration, malformed/oversized files and containment failures. All three UI surfaces must show the same work product and exact notebook. Test ordinary report/download regressions. On the real service, show correct active notebook and connected kernel, execute harmless disposable Python and R probes identifying PUTER, save/reopen, and verify output. Test remote Safari/iPad path, auth renewal, missing R kernel, stopped service recovery and on-boot recovery through a coordinated restart. Emulation alone is labeled as such, not iPad proof.

Distribute the launcher, converter, registry/API/UI integration, setup/capability checks, service-lifecycle support and synthetic tests with Anchor; distribute producer registration instructions and compatible helper calls with the affected skills. Resolve installed package paths, not C:/dev. Skill-produced artifacts must use the common contract whether the skill is launched inside or outside Anchor; without Anchor, emit portable relative artifact/registration metadata for import and explain that live launch requires host setup. Record a supported-version/platform matrix; Windows is the first proven host, and other hosts cannot be advertised until their setup/lifecycle adapter is tested. Build from an explicit package allowlist excluding John's projects, notebooks, settings, journals, transcripts, logs, screenshots and secrets. Verify archive contents and clean install in a fresh profile using only synthetic examples. No private lesson file is a distributable fixture.

Roll out the generic implementation first against the private classroom root, backing up register/associations and retaining old launch links for rollback. A collaborator clean-install gate is also mandatory before claiming portability. No notebook/source deletion on rollback. Steward/Foundry registration instructions and scripts change only through the formal improvement cycle. No code or service changes during this planning request.

Needed because a launch URL alone does not make a produced script discoverable or durable; dropping registration, provenance or startup proof repeats the reported failures. Deployment-local setup and clean-install checks are needed because John requires collaborators to receive the capability without his data. Cut: local/remote IDE, other runners, automatic per-project lab spawning, silent package installation, cell-marker parsing, Rmd conversion, multi-user hosting and automatic execution on open.
