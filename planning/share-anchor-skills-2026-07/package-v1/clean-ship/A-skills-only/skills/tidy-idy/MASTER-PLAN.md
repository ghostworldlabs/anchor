**A. # Master Plan (draft)

**North Star:** Make a project's Tidy-Idy button in Anchor launch a background hygiene pass and open a project-tied Triage Panel presenting everything found — files to REMOVE, files to SAVE/COMMIT, and folder REORGANIZATIONS — as human-approvable decisions, applying only what the human approves as ONE git commit per Apply (undo = git revert), never losing work git holds and never acting without approval. The tidy-idy engine is EXTENDED, NOT FORKED, to add save-detection and reorg proposals and to run on ordinary (non-Foundry, possibly non-git) folders while preserving its removal pipeline and every safety invariant.

## Success criteria
- One-click background run, project-scoped: clicking Tidy-Idy on project P starts a headless run over P's folder (like Gandalf), shows a live running state, and on completion opens a Triage Panel whose header unmistakably identifies P (name+path+git status+run#); a run never touches another project.
- Three finding classes from real analysis: removals each carrying the real Attacker+Judge verdict; save/commit candidates (untracked + uncommitted-modified); reorg proposals rendered as before->after trees. A failed analysis is shown LOUDLY, never a fake-clean panel.
- Nothing applied without approval: per-item/per-set approval then Apply lands all approved changes as ONE git commit (undo = git revert); protected classes (SKILL/README/tests/bin/journal/North-Star) never offered for removal.
- Runs on ordinary folders honestly: no North-Star file -> age/duplicate/orphan/untracked heuristics (labelled); non-git -> offer git init or mark advisory/read-only (no silent mutation); dirty tree handled not refused.
- Extend-don't-fork + green: reuses tidy-idy scanner/hygiene/analyze/debate/remove/compress modules + Anchor job_runner/Gandalf run path + Zombie-Sentinel-style GUI serving; the tidy-idy suite and new tests are green; existing substrate first.
- Investigator terminal tile (like Zombie Hunter): the panel includes an 'Investigate with an agent' tile opening a seeded terminal (Claude, toggle Gemini) loaded with the tidy-idy skill AND a briefing of the CURRENT report, tied to the same project.
- Report archive/history: every run's report is persisted per project newest-first (Gandalf run-index pattern); previous reports are kept as browsable references and never overwritten.

## Owned v1 decisions (tradeoffs stated here, surfaced verbatim in the panel)
1. **One commit per Apply, all-or-nothing.** An Apply compiles EVERY approved finding — removals, saves, and reorgs together — into a single commit built in a temporary index; if any operation fails mid-compile the entire Apply aborts and commits NOTHING. Tradeoff accepted: one bad operation blocks the whole batch (the user retries a narrower selection) in exchange for undo always being exactly one `git revert`.
2. **Undo is revert-or-refuse.** Undo never force-overwrites the working tree or later commits. If `git revert <tidy-commit>` cannot apply cleanly, Tidy-Idy refuses and shows the 'Undo blocked — resolve manually' view; the destructive per-file `git checkout <tidy-commit>^ -- <path>` fallback is banned. For tidy commits containing SAVE operations, undo = the clean revert PLUS the specified re-materialization compensation of decision #8 — still never destructive. Tradeoff accepted: some undos require manual resolution; none can destroy work.
3. **Removal eligibility is tracked-AND-clean.** In a git repo, any path with staged, unstaged, or untracked modification is hard-excluded from the REMOVE class before the LLM debate ever runs; such paths can appear only as SAVE findings. Removing what git does not already hold would violate the North Star, so it is impossible by construction. Untracked junk the debate would want removed follows the canonical table's untracked-REMOVE row: offered as SAVE now (git comes to hold it), REMOVE-eligible next run — destruction only ever happens after git holds the content, and each step undoes as its own pure single revert.
4. **Non-git mutation is Bootstrap-only, and Bootstrap is its own Apply.** Without git there is no undo=revert, so v1 never mutates a non-git folder except through the single user-approved Bootstrap Apply (canonical table's Bootstrap row): `git init` + starter .gitignore + `git add -A` + baseline commit B — one commit, a fixed op-set never mixed with findings, so plan compilation for findings ALWAYS runs against an existing repo. Bootstrap undo is trivial and honest: while HEAD==B, delete .git plus the starter .gitignore (bit-identical pre-state); refused after any later commit exists (removing .git would then discard work git holds). Tradeoff accepted: non-git users must bootstrap (or consume advisory reports) and re-run before Tidy-Idy touches any file.
5. **Reorg v1 Apply gating is leaf-only AND zero-hit.** Only leaf/asset-directory moves whose whole-tree reference scan finds zero hits are applyable; nonzero-hit proposals render as advisory and cannot be applied in v1. Tradeoff accepted: deliberately low reorg coverage in exchange for zero applied moves that can break a reference.
6. **Scan is zero-write.** The analysis pass writes nothing under the project root (the run's report directory is the sole, tripwire-excluded exception); even the starter .gitignore is compiled into Apply.
7. **git:null is a contract, not a crash.** Every git-dependent stage defines explicit no-op/advisory semantics when no repo exists, asserted by a named test (git-null-contract.test.mjs).
8. **SAVE undo is revert plus ONE specified compensation.** A pure `git revert` of a commit that saved a file would delete (untracked SAVE) or downgrade (modified SAVE) the working copy; so undo of a tidy commit containing SAVE operations is DEFINED as: the clean revert, then re-materialize each SAVE'd path from `<tidy-commit>:<path>` into the working tree UNSTAGED — restoring the exact pre-Apply state. The compensation is deterministic, journaled, writes only content git permanently holds, and applies ONLY to SAVE paths; REMOVE and MOVE undo remain pure revert. Tradeoff accepted: undo of SAVE-containing commits is not a single git command, in exchange for undo meaning 'exact pre-Apply state' for every class.
9. **Secrets are hard-blocked from SAVE.** A secret-flagged candidate has NO approval path — not bulk, not individual click-through. The tool proposes instead: (a) an approvable add-to-.gitignore Apply operation (a tracked-file edit, pure-revert undoable), (b) copyable relocation guidance (.env/secret store outside the tree), (c) a per-path false-positive override in .tidy-idy.toml that takes effect only on the NEXT run — deliberate and auditable, never a click-through. Tradeoff accepted: a real-but-odd credential file needs a config edit to commit; no key can ever be committed by a click.
10. **One snapshot is the only time authority.** Each run takes a single run snapshot S = {HEAD sha (or null), the in-scope path set (root minus excluded subtrees minus reportDir), per-path (size, mtime), content hashes added lazily for finding paths}. The read-only tripwire, SAVE finding identity, and Apply-time revalidation are all comparisons against S — no stage takes its own ad-hoc snapshot, so 'changed since scan' means exactly one thing everywhere.

## Canonical Apply pipeline (normative state-transition table)

There is exactly ONE Apply pipeline; every finding class is a row through the same five steps, and every mutating Apply runs against an EXISTING repo (H = pre-Apply HEAD, C = the tidy commit, S = the run snapshot):
1. Acquire the project-root lock; assert HEAD == S.head.
2. Revalidate every approved finding against S (content hash, existence, porcelain status class unchanged — including 'no newly-staged changes'); mismatches drop as 'stale — re-run'.
3. Compile all survivors into ONE temporary index (GIT_INDEX_FILE seeded from H's tree; zero working-tree writes): REMOVE drops entries, SAVE runs `git hash-object -w` on working-tree content and adds entries, MOVE re-paths entries. Any failure aborts ALL: temp index discarded, nothing committed, working tree and user index untouched.
4. Write exactly one commit C via `git commit-tree` (parent H); advance the branch by compare-and-swap `git update-ref refs/heads/<branch> <C> <H>` — fails, aborting cleanly, if HEAD moved.
5. Realize the working tree AND reconcile the user's index with ONE native mechanism: `git -C <root> checkout --no-overlay <C> -- <approved pathspecs>` — updates index and working tree for exactly the approved paths and deletes paths absent from C. The sync is a pure idempotent function of (C, pathspecs): journaled, retried on interruption, never `reset --hard`.

Probed sync behaviors: a locked working-tree file (Windows) exits nonzero → per-path journal state + idempotent retry, and the commit and ref are already durable so no content is at risk; a dirty index is safe because unrelated staged entries are pathspec-excluded and an approved path with newly-staged changes was already dropped in step 2, so step 5 never overwrites staged work; a case-insensitive filesystem is probed at compile time via `core.ignorecase`, and case-only renames or case-colliding MOVE targets are refused (rendered advisory) in v1.

| Row | Pre-state | Compiled operations | Post-Apply (HEAD / index / working tree) | Exact undo result | Loss check |
|---|---|---|---|---|---|
| tracked REMOVE (git) | p tracked-and-clean, blob b at H | temp index drops entry p | HEAD=C (tree lacks p); index entry p removed; working file deleted by step 5 | `git revert C` restores p bit-identical from b — pure revert | b reachable from H forever; one commit |
| untracked REMOVE (git) | p untracked | ROW DOES NOT EXIST (decision #3): p is offered as untracked SAVE in run N; after commit C_N it is tracked-and-clean and takes the tracked-REMOVE row in run N+1 | n/a | each of the two Applies undoes as its own pure single revert | git holds the content (C_N) strictly BEFORE any deletion; one commit per Apply preserved |
| untracked SAVE (git) | p untracked with content c; index lacks p | `git hash-object -w` c → b; temp index adds p=b | HEAD=C (holds p=b); index p=b; working file byte-unchanged | `git revert C` (removes p from tip/index/worktree) + decision-#8 compensation: `git cat-file blob C:p` re-materialized to the worktree UNSTAGED → exact pre-Apply state | c permanently held at C; compensation writes only git-held content |
| modified SAVE (git) | p tracked as b_old at H; worktree holds c_new unstaged | `git hash-object -w` c_new → b_new; temp index sets p=b_new | HEAD=C (p=b_new); index p=b_new; worktree unchanged (=c_new) | `git revert C` (tip/index back to b_old) + compensation re-materializes c_new from C:p into the worktree unstaged → exact pre-Apply dirty state | b_old held at H and c_new held at C, both forever |

The non-git column of every finding row is UNREACHABLE by construction: plan compilation asserts ctx.git ≠ null, and the only Apply a non-git folder can ever receive is Bootstrap — after which the panel prompts a fresh run and every row uses the git column above.

Reviewer obligation: every row is falsifiable. The Phase-8 matrix contains one adversarial cell per row that attempts a concrete losing sequence of user actions (edit-during-Apply, stage-during-Apply, lock-a-file-mid-sync, undo-after-later-commits, Bootstrap-undo-after-new-work); any sequence that loses content git holds is a release blocker.

Everything downstream (new stages, honest failure rendering, ordinary-folder modes) depends on the pipeline being explicit stage functions over a context object with a uniform result contract, analysis being provably non-mutating, and protection being enforced before findings exist (Integrated #2–#6, #11, #12, #16, #39; Mitigations #3, #6, #8, #9).

**Near-term specifics:**

- Define the stage result envelope as a typed contract: {status: 'ok'|'failed'|'partial', coverage: {scanned, skipped, errored}, findings: [], errors: []}; the orchestrator computes the run's terminal state as the WORST stage status and persists the full run envelope as the single source the renderer will consume.
- Make celebratory-clean structurally unreachable: the run envelope exposes isClean only when every stage is status=ok with complete coverage; there is no findings-count path to a clean verdict.
- Declare and enforce the scan zero-write invariant (Owned decision #6): the analysis pass performs ZERO writes under the project root — no starter .gitignore, no compression output, no cache files; the run's reportDir is the sole exception and is excluded from both scan and tripwire. All mutation code is confined to the (not-yet-built) Apply executor module.

The read-only tripwire is 'post-analysis metadata equals S' — any delta aborts the run with status=failed and a diff of exactly what changed; S is persisted in the envelope and is the same object SAVE identity and Apply revalidation later compare against, so no stage carries its own ad-hoc snapshot.
- Demote hygiene/compress to a proposal stage: agent.md/agent_hist.md compression is computed in memory and emitted as a finding with a rendered diff; the analysis pass never writes it.

## Phase 3 — Phase 2 — Save Detection, Secret Triage, and Ordinary-Folder Modes

Serves criteria 2 and 4. Adds the second finding class (SAVE) on real git evidence and makes runs on ordinary folders honest — heuristic findings labeled and defaulted-unchecked, non-git folders offered init-with-preflight or advisory read-only, dirty trees handled not refused (Integrated #10, #13, #20–#22, #34, #37; Mitigations #2, #4-preflight-portion, #11, #13).

**Near-term specifics:**

- Implement per-file dirty-overlap gating on SAVE candidates: if current content differs from analyzed content or the path has staged changes, the finding is flagged with the exact diff of what WOULD be committed (or refused per config); blind `git add <path>` is structurally impossible.
- Enforce the removal-eligibility contract (Owned decision #3): before the attacker/judge debate ever sees a candidate, any path with a staged, unstaged, or untracked modification per porcelain is HARD-EXCLUDED from the REMOVE class and recorded in the envelope's exclusion log with its porcelain evidence — it may surface only as a SAVE finding. Only tracked-and-clean paths reach the removal debate, so a REMOVE can never delete work git does not already hold. Untracked junk the debate would remove is surfaced as a SAVE finding annotated 'save now — removable next run' per the canonical table's untracked-REMOVE row: once its SAVE commit lands, the path is tracked-and-clean and eligible as a tracked REMOVE in the next run.

Size/binary-flagged findings keep quarantine semantics: excluded from bulk-approve, individually confirmable.
- Implement heuristic mode for folders without a North-Star file: age/duplicate-hash/orphan/untracked heuristics emit findings labeled 'heuristic candidate' with raw evidence verbatim; the attacker/judge debate is re-scoped to argue evidence sufficiency; heuristic-only findings default to UNCHECKED.

- Encode the dirty-tree policy: dirty trees never block scan; the run envelope records dirty status so the panel can explain per-file Apply gating.
- Begin assembling the labeled corpus (5–10 real messy folders with hand-labeled remove/keep ground truth) now, so the Phase-8 precision gate has data; corpus lives in test fixtures with labels in JSON.

**Deferred (explicitly):**
- The heuristic precision CI gate itself (Phase 8) — heuristic mode does not SHIP until it passes; in this phase it exists behind the mode flag only.
- Removal-verdict caching (Phase 4).
- All rendering of these finding classes (Phase 5).
- Reorg heuristics entirely (Phase 7).

## Phase 4 — Phase 3 — Apply Executor: Identity, Compiled Plan, Revalidation, Undo, Lock

Serves criterion 3 (nothing applied without approval; EXACTLY ONE commit per Apply; undo = git revert) and closes the largest failure surface: the only code that mutates. Finding identity, the single-commit all-or-nothing compiled plan, staleness revalidation, revert-or-refuse undo, the advisory lock, and the forensic journal all live here (Integrated #7–#10, #14, #15, #17, #38; Mitigations #4, #5, #16, #17, #18). This phase implements the canonical Apply pipeline table verbatim; the table is the executor's normative spec and its rows are the unit-test matrix.

**Near-term specifics:**
- Implement the finding identity contract: ID = hash(run_id, action, path, content_hash), generated at emission, round-tripped in full by the panel; Apply refuses any ID it cannot match exactly — approval by index or bare path is impossible by construction.
- Build Apply as ONE compiled plan producing ONE commit (Owned decision #1): ALL approved findings — removals, saves, and reorgs together — are topologically ordered (mkdir before move-in, moves before deletes-at-old-paths) and compiled into a single temporary index via GIT_INDEX_FILE, seeded from HEAD's tree so the user's index is never touched: removals drop index entries, saves hash-object working-tree content into new entries, moves re-path entries; exactly one commit object is written from that temp index with HEAD as parent.
- Make the plan all-or-nothing (abort-all, commit-none): the entire compile runs in temp-index space with zero working-tree writes; if ANY operation in a mixed batch fails mid-compile, the whole Apply aborts — temp index discarded, no commit created, working tree and user index bit-identical to pre-Apply. Only after the commit object exists is the branch advanced by compare-and-swap (`git update-ref refs/heads/<branch> <C> <expected-HEAD>`, failing cleanly if HEAD moved), and working-tree realization + user-index reconciliation is ONE native mechanism — `git -C <root> checkout --no-overlay <C> -- <approved pathspecs>` — a pure idempotent function of (C, pathspecs) that is journaled, retried on interruption, and surfaced loudly with exact per-path state if incomplete (never silently half-applied, never auto-`reset --hard`). Its three probed behaviors — locked file (idempotent retry, commit+ref already durable), dirty index (unrelated staged entries pathspec-excluded; approved paths with staged changes already dropped as stale), case-insensitive filesystem (`core.ignorecase` probe refuses case-only/case-colliding targets) — each get a fixture test.
- Implement per-file staleness revalidation inside Apply as a comparison against the run snapshot S (Owned decision #10): each approved finding is re-checked (content hash equals S's hash, path exists, porcelain status class unchanged — including no newly-staged changes), and HEAD == S.head is asserted under the lock immediately before the ref update; mismatches are dropped from the commit and surfaced as 'stale — re-run' in the result.
- One Apply = one commit, period: sections (removals / saves / reorgs) are approval-UI groupings only, never commit boundaries; the commit message encodes run ID + all finding IDs grouped by section for forensic diffing. The control plane permits ONE Apply per run — findings left unapproved are picked up by a re-scan (cheap via the verdict cache), which produces a new run and its own single-commit Apply.
- Implement revert-or-refuse undo (Owned decision #2): 'Undo (git revert <tidy-commit>)' either applies cleanly or is REFUSED — there is no destructive fallback and no code path that force-overwrites the working tree or later commits; the per-finding `git checkout <tidy-commit>^ -- <path>` degrade is explicitly banned. Revert cleanliness is tested without mutating the user's tree via `git merge-tree` (or a dry-run in a disposable temp worktree), never via `revert --no-commit` on the live checkout. When the tidy commit contains SAVE operations, undo executes the clean revert PLUS the decision-#8 compensation — re-materialize each SAVE'd path from `<tidy-commit>:<path>` into the working tree unstaged, immediately after the revert inside the same lock window — restoring the exact pre-Apply state; REMOVE and MOVE paths remain pure revert.
- Enumerate and handle every revert failure branch: (a) dirty working tree overlapping revert paths → refuse and list the overlapping files; (b) later commits conflict with the revert → refuse and list the conflicting commits and paths; (c) tidy commit already reverted → no-op with explanation; (d) HEAD moved but the revert merges cleanly → allowed. Every refusal renders the named 'Undo blocked — resolve manually' panel: the exact conflicting paths/commits plus a copyable `git revert -n <sha>` command for the user's own terminal; the state-machine output feeds panel copy so it never over-promises.
- Implement the per-project-root advisory lock: lockfile with PID + job ID honored by scan runs AND Apply; Apply re-verifies HEAD unchanged inside the lock window immediately before committing.
- Re-run the protection predicate inside Apply as defense in depth (same module as Phase 1, second call site).
- Write the run journal: every Apply logs the compiled operation plan, per-op result, and resulting commit sha into the run's archive directory.
- Unit-test the executor against fixture repos for: mixed-batch mid-compile failure (aborts ALL — no commit, working tree and index bit-identical to pre-Apply), stale finding dropped, protected path injected into the request (refused), advisory-mode/git-null request (refused, per git-null-contract.test.mjs), lock contention (second Apply queued/refused), and every undo branch — clean revert, dirty-overlap refusal, later-commit-conflict refusal, already-reverted no-op — asserting the working tree is never force-overwritten; plus one test per canonical-table row: tracked-REMOVE round-trip, the untracked-REMOVE two-Apply sequence, untracked-SAVE and modified-SAVE undo-with-compensation restoring the exact pre-Apply (dirty) state bit-for-bit, reorg-MOVE round-trip, and both Bootstrap-undo branches (HEAD==B allowed, past-B refused) — each written as an attempted losing sequence that must fail to lose data.

**Deferred (explicitly):**
- The HTTP control plane around Apply — capability token, persisted pending→applying→done state machine, replay idempotency (Integrated #19) — is deferred to Phase 5 where the server exists; this phase exposes Apply only as a library API with the refusal predicates built in.
- Registering the lock as an Anchor job-runner resource claim (Phase 4).
- UI staleness banners and disabled-bulk-Apply behavior (Phase 5).
