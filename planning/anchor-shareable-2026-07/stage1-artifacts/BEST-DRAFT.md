# Master Plan (draft)

**North Star:** Transform the integrated Anchor system (the Anchor app + the researchPrime/Crucible/Foreman trio + the foundry skills + their operating conventions) from a single-user, single-machine tool into a package a trusted collaborator can obtain and run on their own Windows/macOS/Linux machine, such that: (1) they receive it as a scrubbed, self-contained bundle that never carries the author's personal or proprietary data; (2) onboarding brings up a working, secure-by-default instance with zero manual token handling; (3) the instance is safe to run and safe to expose (no unauthenticated data-read or code-execution surface); (4) the agent trio behaves identically to the author's (same governance, status discipline, skill-immutability); and (5) none of this regresses the durability, honesty, and safety engineering the system already has. Non-goals: the WAL inversion (deferred), multi-user/multi-tenant on one instance, OS-level agent sandboxing, a frontend rewrite, cloud hosting, an observability stack, re-architecting the trio/foundry skills' internals.

## Success criteria
- Secure-by-default: a freshly-onboarded instance behind a loopback reverse proxy returns 401 to a tokenless request on every data-plane, terminal, and dir-browse route, refuses every unauthenticated WebSocket upgrade before the 101, and the bypassPermissions build lane is unreachable without the token; no unauthenticated read/filesystem-enumeration/code-execution surface remains; every allowed exposure posture appears in the normative exposure matrix (Phase 3) — every row of which is a channel that is authenticated end-to-end (loopback kernel, OS-ACL-bounded local IPC, SSH host-key, Tailscale WireGuard identity; no self-signed-TLS surface ships at all) — and everything off-matrix is refused with no override flag.
- Zero-friction token: the author and each collaborator never manually find, read, or type the master token — it is auto-provisioned + persisted locally at onboard, auto-used by the local browser, survives restarts; the master token never leaves the engine process and its mode-0600 file — it appears on no process argv, in no spawned child's environment, in no URL (not even a fragment), and in no log; even the `anchor` CLI never reads or transmits it, because the CLI's credential is its OS identity on the local control channel (Phase 3). The interactive bootstrap path carries **zero secrets of any kind end-to-end**: no bootstrap credential ever exists in any file, on any argv, or in any URL, and the claim POST is same-origin by construction (Phase 3). The ONLY human-carried secret in the whole system is the headless path's one-time pairing code: single-use, 10-minute expiry, globally attempt-capped per code (never per-IP), and useless after claim or through any interception attempt — no sanctioned posture offers a MitM position (Phase 3's secret inventory is the normative statement).
- No-leak distribution: bundle composition is allowlist-driven and deny-by-default (a file ships only if explicitly listed); the only share channel is the scrubbed release repo containing none of the author's personal/proprietary files or git history; import anchor_gui inside the staged bundle boots (smoke-gated); updates arrive as fast-forward-only pulls of an append-only scrubbed release branch executed as an atomic update transaction whose rollback is **provably offline and local-state-only** — every recovery asset (recorded SHA, renamed node_modules snapshot, stash, moved-aside untracked/ignored files, exported divergent commits) is captured locally before any mutation, and no failure path requires the network (Phase 4). The shipped dependency tree is **pure-JS by policy** — no native compilation, no install scripts — so `npm ci` succeeds on a machine with no compiler toolchain, and CI enforces it (Phase 4).
- Works-on-arrival cross-platform: a collaborator on Windows and macOS/Linux goes bundle -> first-contact integrity ceremony -> onboard -> live dashboard via one documented path, on a **pristine machine** — the acceptance VMs start with no git, no gpg, and no compiler, and **every command in the documented path exists on the target machine at the moment it is typed** (any tool a step assumes is installed by an earlier step whose provenance is stated inline; the ceremony needs only git — installed per the out-of-band message — and ssh-keygen, which ships with Windows 10/11, macOS, and mainstream Linux; **gpg is never used anywhere in the system**); missing prerequisites surface as one upfront actionable message; release N -> N+1 follows the committed update-transaction state machine — including the dependency-sync, local-edits, **locally-committed-divergence**, foundry-edited-skill, park, offline-rollback, and interrupted-resume cases — with **zero operator-typed git commands after first contact** (the 'no manual git surgery' promise is kept, not withdrawn: every remediation surface is an `anchor` command, and the acceptance suite asserts no doc, prompt, or error message ever prescribes a git or openssl command to the operator; the sole, explicitly scoped exception is the one-time first-contact ceremony's verification commands, which by design run before any shipped code is trusted).
- Identical agent behavior: trio + foundry skills run under the same governance — the status-discipline **hybrid** (engine-emitted 10-min status blocks + engine-owned prompt-preamble grounding; same transcript shape by construction; the resolution, where the grounding instruction lives, and its named NS(4)/NS(5) trade-off are stated explicitly in Phase 6), skills read-only/foundry-only-edit, driver-init self-configures to the host's engines.
- No durability regression: the durability cluster (CLI+secondary atomic writes, cross-process lock, torn-index rebuild-from-pointers, boot-reaper owner-set) is closed and covered under the explicit per-OS durability contract (Phase 2) — including the Windows contention bound, which covers file renames AND the directory rename/delete operations the update transaction depends on, with its per-OS pinning assertions — with the pinning suite green on NTFS as well as ext4/APFS; existing telemetry/narration/reaper-safety invariants hold.
- Money-safe + clean: the test suite cannot spend real money without explicit opt-in (fail-closed); shipped tree free of dev debris and dependency-doc contradictions.

Seven phases, sequenced by dependency and risk: first pin the invariants and stand up 3-OS CI so nothing can regress silently; then do the path/config indirection and OS-abstraction work — under an explicit per-OS durability contract — that every later wave depends on; then invert the security model to default-deny with a **secret-free interactive bootstrap** (the claim flow walked request-by-request: origin, CORS posture, argv contents, prefetcher behavior, headless path), the **WebSocket-upgrade and CLI→daemon credentials written as concrete request/response flows**, and a normative exposure matrix naming only end-to-end-authenticated channels; then build the deny-by-default allowlisted bundle with its leak-scan and boot-smoke gates wired into CI, a pure-JS dependency policy so installs never need a compiler, an append-only scrubbed release branch as the update topology, and the update transaction engineered as an explicit **whole-system state machine** — every step with its named failure modes, a provably offline local-state-only rollback, diverged-local-commit capture, an explicit answer for foundry-edited skills, and the verify gate running on the final assembled tree — with zero operator-typed git; then the collaborator onboarding path (doctor, capability probe, first-run acceptance on pristine no-git/no-gpg/no-compiler VMs including an SSH-to-Linux-server scenario, and a scripted Windows first-week walkthrough); then engine-enforced governance parity; and finally release integrity — anchored in an out-of-band first-contact trust ceremony whose payload is written out verbatim in this plan, which requires only tools whose provenance the payload itself states, and which trusts nothing inside the clone — plus one external red-team pass per cycle. Phases 1-4 carry Stage-2-seeding specifics (named modules, commands, tests, gate semantics, the update-transaction step table); later phases state their contracts concretely but defer implementation detail to Stage 2. Every phase maps to named success criteria; the North-Star non-goals (WAL inversion, multi-tenant, OS sandboxing, frontend rewrite, cloud hosting, observability stack) stay excluded throughout.

## Phase 2 — Path/Config Indirection and OS-Abstraction (the portability substrate)

Serves criteria 4 and 6. M1 and M3 make indirection an explicit prerequisite of scrubbing, not a byproduct; M5 ports durability primitives behind per-OS implementations governed by an explicit, pinned per-OS contract. Nothing in Phases 3-5 works on a foreign machine layout until this lands.

**Near-term specifics:**
- Single bundle-root resolution module (idea 8 / M3): one module (e.g. `lib/roots.mjs`) exposing the only sanctioned way to resolve skill/sibling/config paths; every import and every spawn is migrated to it; a lint/CI grep from this wave forward forbids literal cross-sibling paths (`C:\\dev\\...`, `/dev/trio/...`).
- One config root with env-derived paths (idea 8 / M1): all state, tokens, logs, and caches resolve under a single per-user config root (platform-appropriate: %APPDATA%/XDG/Library) overridable by one env var; execute every strip/parameterize/refactor item from the Phase-1 census. This root lives OUTSIDE the repo tree — a hard prerequisite for the Phase-4 update transaction (updates must never touch user state).
- Per-OS durability contract (idea 20 / M5), stated concretely and pinned:
  - POSIX (ext4/APFS): atomic write = temp file created in the target's own directory + fsync(temp fd) + rename(2) + fsync(parent-directory fd).
  - Windows/NTFS: there is no usable directory-handle fsync from Node (fs.fsync on a directory handle is not portably obtainable) — the contract substitutes: temp file created in the target's own directory (same NTFS volume, so rename can never degrade to copy+delete), fsync(temp fd) (FlushFileBuffers), rename via Node fs.rename → MoveFileEx(MOVEFILE_REPLACE_EXISTING) (atomic same-volume on NTFS), then open+fsync the DESTINATION file post-rename to force NTFS metadata-journal ordering — that post-rename fsync is the Windows replacement for parent-dir fsync.
  - Rename contention bound (Windows AV/indexer/Search), stated realistically: real-world AV and Windows Search can hold a handle on a just-written file for MULTIPLE SECONDS, not milliseconds. The contract: EPERM/EBUSY/EACCES on rename retries with decorrelated exponential backoff starting at 10ms, capped per-attempt at 1s, with a TOTAL bound of 15s (configurable upward, never downward) — then fails LOUDLY with the file path, the errno history, and remediation text naming AV exclusion as the likely fix (the remediation is descriptive advice about AV configuration — never a git or shell command for the operator to run). A copy+delete fallback is forbidden (non-atomic) and lint-banned. This retry loop exists ONLY on Windows: on POSIX the contention class does not exist, and the contract asserts the retry path is structurally absent there (no silent divergence between platforms). **The same contention-bound module covers DIRECTORY operations — directory rename and recursive delete — because Phase 4's update transaction leans on both (the `node_modules` snapshot rename, the partial-install delete, the snapshot cleanup): same backoff schedule, same total bound, same loud failure; and for recursive delete ONLY, a bounded-failure escape hatch exists — if a directory cannot be fully deleted within the bound (AV holding a file deep inside), the engine renames it aside to a `*.trash-<seq>` name and schedules deferred cleanup at next boot, so no transaction step ever wedges on a locked directory. Rename-aside is sanctioned for DELETE (where atomicity is not needed) and remains forbidden as a substitute for atomic file replace.**
  - Lock: O_EXCL creation of a lockfile containing a start-time+PID liveness pair; staleness compares BOTH (never PID alone); no flock/LockFileEx semantics are assumed portable.
  - What the pinning suite asserts, per OS (via the Phase-1 fs shim + a crash-point harness): on POSIX — the exact 4-step sequence in order, a simulated crash between any two steps leaves either the complete old or complete new content (never torn), and the Windows retry path is never invoked (asserted absent); on Windows — no directory fsync is ever attempted, the temp file is same-volume with its target, the post-rename destination fsync is observed, AND the contention bound is exercised: an injected EPERM sequence spanning a simulated 5s of failures still succeeds within the 15s bound, an injected sequence exceeding the bound produces the loud failure with errno history (not a hang, not a silent copy+delete), the backoff schedule observed matches the contract, and the directory-delete escape hatch is exercised (an undeletable directory ends renamed-aside with deferred cleanup recorded, never a wedged transaction); on all three — lock O_EXCL semantics, start-time+PID stale-lock takeover, and the boot-reaper owner-set behavior unchanged. 'No durability regression' on NTFS means this suite green on windows-latest — a CI verdict, not a prose claim. The suite must stay green on all three OSes against the new layer before merge.
- Shell-free spawning with a journaling allowlist spawner (idea 12 / M8): replace every shell-syntax-dependent spawn with direct argv-array child_process invocations through ONE spawn module (no cmd/sh string interpolation anywhere), eliminating quoting divergence as an onboarding failure class. Child environments are CONSTRUCTED from an allowlist, not inherited wholesale. The spawn module journals every child's full argv and constructed env to a test-visible log when running under test — this journal is what makes Phase 3's token-hygiene CI test both passable and complete: because the lint pack forbids any spawn outside this module, the journal is by construction a total record of what crossed into every child, including the browser-launch argv on the bootstrap path.

**Deferred (explicitly):**
- The scrub/bundle builder itself (Phase 4) — this phase only makes the tree scrub-ABLE.
- Cross-skill spawn smoke from a foreign root (Phase 4, needs the staged bundle to exercise).
- driver-init host-probing hardening (Phase 5) — Phase 2 only guarantees its spawns are shell-free and root-resolved.

## Phase 3 — Default-Deny Security Model and the Secret-Free Zero-Friction Bootstrap

Serves criteria 1 and 2 directly. M9 inverts the model to default-deny; M6 makes the bootstrap out-of-band-anchored and single-use; M13 makes exposure degrade loudly under a normative matrix. This precedes bundling so no bundle ever ships with an open surface. The bootstrap is specified here as ONE coherent secret system — every secret named, with its birth, residence, transit, lifetime, and revocation — governed by four design laws that hold on every path, interactive or headless:

1. **No secret ever rides a process argv** — on any path, for any process.
2. **No bootstrap credential ever exists in a file.** The only secrets at rest anywhere are the master token's 0600 file and the session store, both under the config root; nothing the claim flow uses is ever written to disk.
3. **No secret ever appears in a URL** — query string or fragment, GET or otherwise. (Browser launchers put the URL on argv; browsers put URLs in history; extensions and prefetchers read URLs. A URL is a broadcast, so it carries nothing.)
4. **Every claim POST is same-origin by construction**: the claim page is served by the engine itself at the same loopback origin the POST targets. CORS is globally disabled — no `Access-Control-Allow-*` header is ever emitted by any route — so a cross-origin claim is impossible both by policy and by the browser's own enforcement.

The master token itself never leaves the engine process and its 0600 file — the browser never receives it; the browser's credential is always a session cookie obtained through the claim flow below; and the `anchor` CLI never receives it either — the CLI's credential is its OS identity on the local control channel below. Nothing in the system ever needs to read the token file except the engine that wrote it.

**Near-term specifics:**
- Default-deny auth middleware (idea 1 / M9): mounted before every handler — HTTP routes, WebSocket upgrades, static file serving, dir-browse; allowlist starts EMPTY and every exemption must be justified in code review.
- Live route-table walker test (idea 2): boots a fresh instance, enumerates every registered HTTP route plus the WS upgrade path, asserts 401/deny for each without a token, asserts the WS upgrade is refused BEFORE the 101 handshake completes, and asserts no route ever emits a CORS-permissive header; runs in the Phase-1 CI matrix so a newly added route can never silently ship open (criterion 1's acceptance test, mechanized).
- Secret inventory (normative — the complete set; a secret or credentialed channel not in this table does not exist):

| Secret / channel | Generated | At rest | Transits | Lifetime | Revocation |
| --- | --- | --- | --- | --- | --- |
| Master token (256-bit random) | once, at onboard, by the engine (in-process CSPRNG) | mode-0600 file (Windows: owner-only ACL) under the Phase-2 config root — nowhere else | NOWHERE — never leaves engine memory + that file; never on argv, in any child env, in any URL (fragment included), in any log, in any HTTP header, or in the browser; even the CLI never reads it | until rotated | `anchor token rotate` — one command; regenerates token, invalidates all sessions |
| One-time pairing code (headless path ONLY; ~10 chars Crockford base32, ~50 bits entropy) | on demand by `anchor pair`, written to the server-side terminal's stdout only — never argv, never a file, never a log; server keeps only a hash in memory | not persisted | typed by the human into the engine-served claim page once; travels only in a same-origin POST body over an authenticated channel (loopback/SSH/Tailscale) — the sole human-carried secret in the system | single-use, 10-minute expiry, **global per-code attempt cap of 5** (identity key is the code, never any client IP) | expires on use, timeout, or the 5th failed attempt |
| Claim nonce (an anti-replay binder, not a credential) | per claim attempt, by the server | server memory | embedded in the engine-served claim page, returned in the claim POST body | single-use, seconds-long expiry | consumed or expired |
| Session cookie (random session id, server-side session record) | on successful claim | HttpOnly, SameSite=Strict cookie in the browser; session record server-side | Cookie header on the authenticated channel only — on HTTP requests AND on the WebSocket upgrade (the browser attaches it to a same-site upgrade automatically; this is the WS credential) | survives restarts via the persisted session store under the config root; idle+absolute expiry documented | logout, token rotation (invalidates all), or expiry |
| CLI control channel (named pipe / UDS — carries NO secret; listed to show nothing else exists) | at engine boot | Windows: named pipe with owner-only DACL; POSIX: unix-domain socket in a mode-0700 dir under the config root | nothing secret transits — the CLI's credential IS its OS peer identity, verified per-connection | lifetime of the engine process | pipe/socket removed at shutdown |
| Armed claim window (server-side state, listed to show nothing else exists) | by onboard / `anchor claim` | server memory only | never | 60 seconds, single success | consumed or expired |

  Note what is ABSENT: the interactive path has no claim grant, no shuttle file, no code — it carries **zero secrets**. The previous shuttle-file design is rejected by law 2 (a secret existed in a file) and law 4 (a file:// page's claim POST is cross-origin, null-Origin); this revision removes the entire class rather than hardening it. Also absent: any CLI-side bearer token — the control channel below makes one unnecessary, which is why the master token's transit row can honestly say NOWHERE.

- Interactive bootstrap (the default), walked request-by-request:
  1. Onboard: engine generates the 256-bit master token in-process and writes it to the 0600 token file. Token bytes now exist in engine memory and that file, and never anywhere else, ever.
  2. Engine arms the claim window: 60 seconds, single success, bound to a fresh claim nonce; this state lives only in engine memory.
  3. Engine spawns the default browser through the Phase-2 journaling spawner with argv = [browser-launcher, `http://127.0.0.1:<port>/onboard`]. **What appears on argv:** a launcher path and a secret-free URL — zero secret bytes; a process listing, browser history, or URL-logging extension learns nothing (this is the entire reason the URL carries no credential).
  4. **Origin of the claim page:** the browser GETs `/onboard`, which the ENGINE ITSELF serves — the page's origin is exactly `http://127.0.0.1:<port>`, the same origin as every API route. The page contains the claim nonce and an inline script. The GET is idempotent and grants nothing. **What a prefetching extension sees:** a secret-free URL; if it fetches the page, it cannot consume the window — claiming requires a POST bearing a custom header, which prefetchers, link-previewers, and AV URL-scanners never send.
  5. The page script POSTs `{nonce}` to `/claim` on the SAME origin, with header `X-Anchor-Request: 1`. **CORS behavior:** the browser attaches `Origin: http://127.0.0.1:<port>`; the server refuses any claim whose Origin is not exactly its own origin. A malicious website's fetch carries that site's Origin → refused; because the custom header makes any cross-origin attempt non-simple, the browser first sends a CORS preflight — which the server always refuses (no `Access-Control-Allow-*` exists anywhere) — so a cross-origin claim never even reaches the handler. A cross-site form post cannot carry the custom header → refused.
  6. **OS peer-credential check (the identity proof, replacing file permissions):** before honoring the claim, the server resolves the loopback TCP connection's peer — the (remote-port, local-port) pair — to its owning process and that process's OS user via the platform TCP table (Windows: GetExtendedTcpTable owning-PID; Linux: /proc/net/tcp socket inode → owning process → uid; macOS: libproc). The claim succeeds only if the connecting process belongs to the SAME OS user as the engine. A second local user racing the window is refused and logged with the peer identity. If the peer lookup is unavailable or ambiguous on a host, the claim REFUSES — fail closed — and the engine directs the operator to the pairing path.
  7. On success: server creates the session record, sets the HttpOnly SameSite=Strict cookie, consumes the window, redirects to the dashboard. On expiry (no-show), the window simply lapses; `anchor claim` re-arms it and re-opens the browser.
  8. Net effect: the human never sees, types, or copies anything, and the interactive path is secret-free end-to-end — nothing in any file, on any argv, in any URL. The residual attacker who can defeat this is same-user local code execution — which is outside the threat model, because that attacker reads the 0600 token file directly; the design goal is that bootstrap adds NO surface beyond what the token file already defines.
- **WebSocket-upgrade authentication, written as the concrete flow (browsers cannot set custom headers on a WS handshake — the design never needs one):**
  1. The dashboard page (same origin, already session-cookied) runs `new WebSocket("ws://127.0.0.1:<port>/ws")`.
  2. The browser emits `GET /ws` with `Upgrade: websocket`, `Host: 127.0.0.1:<port>`, `Origin: http://127.0.0.1:<port>`, and — because the upgrade is initiated from a same-site page — the `Cookie:` header carrying the SameSite=Strict session cookie. That cookie IS the WS credential; no token, no URL parameter, no subprotocol smuggling.
  3. The server, BEFORE completing the handshake, checks in order: Host ∈ the strict allowlist (else refuse); Origin exact-match against its own origin — never wildcard, never null (else refuse); session cookie resolves to a live session (else refuse with 401). Only then does it return `101 Switching Protocols`. Every refusal happens pre-101 — no socket ever opens unauthenticated (the route-walker test asserts exactly this).
  4. Why this is CSRF-safe without the custom header: a hostile page attempting `new WebSocket` to 127.0.0.1 presents ITS OWN Origin → refused at step 3; independently, SameSite=Strict means the browser would not attach the session cookie to a cross-site-initiated upgrade at all — two independent kills for the same attack. The `X-Anchor-Request` rule is therefore scoped, normatively, to HTTP state-changing routes; the WS upgrade's equivalents are the Origin exact-match + cookie pair above.
- **CLI→daemon credential, written as the concrete flow (the exact mechanism, and why no secret exists on it):** every `anchor` verb (update, edits, claim, pair, token rotate, doctor's resume-or-rollback) talks to the running engine over a LOCAL IPC control channel, never over the HTTP port: on Windows, a named pipe `\\.\pipe\anchor-<per-install-id>` created with an owner-only DACL; on POSIX, a unix-domain socket at `<config-root>/run/anchor.sock` inside a mode-0700 directory. Per-connection, the engine verifies the peer's OS identity before reading a single byte of request: Windows — GetNamedPipeClientProcessId → open process token → compare user SID to the engine's own SID; Linux — SO_PEERCRED uid; macOS — LOCAL_PEERCRED. Same-user → the connection is fully authorized (the OS ACL plus the peer check are the credential); different user → refused and logged. **No secret transits, none is stored, and the master token is never involved** — which is what keeps the token's inventory row at 'transits NOWHERE'. If the engine is not running, the CLI verbs that can act alone (doctor, the update transaction's resume-or-rollback) operate directly on the config root under the Phase-2 cross-process lock; there is no fallback that moves a credential over HTTP, ever.
- Headless/remote bootstrap (SSH-tunnel and no-local-browser hosts): `anchor pair` generates the pairing code, prints it to its own attached terminal via stdout (never argv, never a file, never a log; server retains only the hash), and arms a 10-minute single-use claim window. The collaborator opens the engine-served claim page through the tunnel — the shipped SSH recipe pins the local forwarded port to the server port, so the page's origin matches the server's Host/Origin allowlist and the claim POST remains same-origin — and types the code into the form; it travels once, in the POST body. The server exchanges it (constant-time hash compare, nonce-bound, single-use) for a session cookie. The master token itself is never displayed, copied, or pasted on ANY path; the 10-minute TTL is sized for a real human on a real SSH session (a 90-second window fails honest users and buys no security a 5-attempt cap doesn't already buy).
- **Pairing-code MitM/replay analysis, stated affirmatively:** on every sanctioned posture the channel is authenticated end-to-end before the code ever transits — loopback (kernel-confined), SSH (host-key-verified tunnel), Tailscale (WireGuard mutual identity). No matrix row offers plaintext or unauthenticated TLS, so **no MitM position exists on any sanctioned path**; and even a hypothetically captured claim POST replays to nothing — the code is single-use, nonce-bound, and dead after first exchange. This property is exactly why the self-signed direct-TLS posture is deleted below rather than kept: a self-signed cert the human cannot verify IS a MitM position, and a pairing code typed through it would be capturable.
- Rate-limiting identity, stated as a design rule (carried from round 2/3, normative): behind the loopback (and behind any SSH tunnel) every request arrives from 127.0.0.1, and X-Forwarded-For is attacker-writable text with no trusted proxy tier to launder it — so **per-IP limiting is rejected system-wide**: no sanctioned posture presents a real, spoof-resistant client IP (loopback and SSH collapse to 127.0.0.1; Tailscale identity is per-node, not per-IP-trustworthy for limiting). The limiter's identity key is always the credential itself: per-code global attempt cap for pairing codes, per-window single-use for interactive claims, per-session for authenticated routes. X-Forwarded-For is never consulted anywhere in the auth path.
- CSRF / SameSite / rebinding hardening on the loopback posture (loopback is NOT treated as inherently safe — any local browser tab can send requests to 127.0.0.1): session cookie is HttpOnly + SameSite=Strict; every state-changing HTTP route additionally requires the custom `X-Anchor-Request: 1` header so a cross-site form post can never qualify (the WS upgrade substitutes the Origin+cookie pair above); strict Host-header allowlist (`127.0.0.1:<port>`, `localhost:<port>`, `[::1]:<port>`) with anything else refused — this closes DNS rebinding, since a rebound hostname presents the wrong Host; Origin checked on every claim POST and every WS upgrade (exact-match own-origin, never wildcard, never null); CORS disabled globally (no cross-origin responses at all).
- Token-hygiene invariants, with a CI test that can actually pass: the invariant — the master token exists ONLY in engine memory and the 0600 file; the pairing code exists ONLY in one terminal stdout and one same-origin POST body; no secret appears on any process argv, in any spawned child's environment, in any file (beyond the token file and session store), in any URL, in any HTTP header, or in any log line. The test mechanics: a scripted onboard runs under the Phase-2 journaling spawner, which records the complete argv + constructed env of every child spawned during onboard (including the browser launch), claim, one agent spawn, one CLI control-channel invocation, and one restart; the test then asserts the master token and the pairing code (and their base64/hex variants) appear nowhere in the spawn journal, nowhere in any file under the repo tree or temp dirs, nowhere in any log, nowhere on the control channel's wire capture, and nowhere in the server's request-line/access logs — and additionally that the browser-launch argv matches [launcher, secret-free-URL] exactly, with no query string and no fragment. Because the lint pack forbids spawning outside the journaling module, the journal is a total record — the test is deterministic, closed over a finite artifact set, and green-able.
- Exposure matrix (idea 25 / M13), normative — every allowed posture is a row, every row is an end-to-end-authenticated channel, and anything off-matrix is refused:

| Bind address / endpoint | Transport / channel identity | Application auth | Verdict |
| --- | --- | --- | --- |
| 127.0.0.1 / ::1 (default) | HTTP, kernel-confined to loopback | session cookie + custom-header + Host/Origin checks on EVERY route; cookie + Origin exact-match pre-101 on the WS upgrade; peer-credential check on claim | Allowed — the default posture |
| local IPC control channel (named pipe / UDS) | OS-ACL-bounded, kernel-confined; per-connection OS peer-identity check (SID/uid must equal the engine's) | none needed — the OS identity IS the credential; carries no secret | Allowed — the only CLI path; local-only by construction |
| loopback, reached via SSH tunnel | SSH supplies encryption + host-key-verified identity | session auth still required (never waived); headless pairing path sanctioned; per-credential caps only (no per-IP — see rate-limiting rule) | Sanctioned remote path; shipped recipe (recipe pins forwarded port = server port so Origin/Host checks hold) |
| Tailscale tailnet interface (explicit `--bind tailscale`) | WireGuard supplies encryption + mutual node identity | session auth still required (never waived) | Sanctioned carve-out (carried from round 2/3); logged loudly at every boot |
| any non-loopback bind (LAN / 0.0.0.0), any transport | — | — | REFUSED unconditionally — **no override flag exists**; the refusal message names the two sanctioned remote recipes (SSH tunnel, Tailscale) with their one-command setup |

  The former `--i-understand-exposure` direct-TLS row is **REMOVED, not channel-bound**: with an engine-generated self-signed certificate, the human has no way to authenticate the channel before their browser sends a credential through it — fingerprint-pinning discipline cannot be assumed of a first-week collaborator — so the tier is not actually securable and does not ship. Wide-area access is SSH or Tailscale, both of which bring their own mutual identity. The carve-out is explicit and principled: the instance still binds only loopback (SSH) or an identity-bounded WireGuard interface (Tailscale), the network layer supplies authenticated encryption, and application token auth is never waived in ANY row.
- Token persistence + recovery (idea 4): session survives restarts via the persisted 0600 file, session store, and cookie; cookie loss on the interactive path is one command — `anchor claim` re-arms the secret-free window and re-opens the browser (the human still never reads or types anything); cookie loss on the headless path re-runs `anchor pair`; rotation is one command (criterion 2 end-to-end).
- bypassPermissions defense-in-depth (idea 29): reachable only with a valid session AND an explicit per-session enable, logged with who/when — beyond the global middleware.

**Deferred (explicitly):**
- External red-team pass against the claim flow, pairing flow, WS upgrade, and control channel (Phase 7 — needs a staged bundle to attack).
- Any direct-TLS exposure posture (self-signed or CA/ACME) — removed from the matrix entirely; reintroducing one would require a channel-binding design and re-entry through Shark review as a plan amendment.
- Multi-user sessions / per-collaborator identity on one instance (North-Star non-goal: multi-tenant).

## Phase 4 — Deny-by-Default Bundle Builder, Scrubbed Release Topology, and the Update Transaction (a whole-system state machine)

Serves criterion 3 (and 7's clean-tree half). M2 mandates allowlist-only composition from a fresh export; M12 makes the scrub a per-commit CI verdict so entanglement regressions are one-line fixes, not archaeology. This phase also commits the exact update topology AND the update transaction — specified below as an explicit state machine: every step with its named failure modes, every recovery **provably offline and local-state-only**, an explicit answer for locally-committed divergence AND for a legitimately foundry-edited skill, and the verify gate running on the **final assembled tree** — so 'pull-to-update' is a mechanism the operator invokes with one command and never steers with git.

**Near-term specifics:**
- Deny-by-default composition (idea 5 / M2): the bundle is composed from an explicit allowlist manifest (`bundle/MANIFEST`: exact paths plus reviewed globs); a file ships ONLY if listed. Staging is a fresh export into a clean directory (NEVER in-place deletion of the working tree), and the build FAILS CLOSED on any tree file that is neither listed nor explicitly marked not-shipped — a new file can never drift into the bundle by default, and dev debris (idea 28) is excluded structurally. Scrub-by-pattern is demoted to defense-in-depth: the leak scanners run ON TOP of allowlist composition and are never the composition mechanism.
- **Pure-JS dependency policy (the no-compiler guarantee):** the shipped dependency tree contains no native modules and no packages with install/preinstall/postinstall scripts or gypfiles; the shipped install mode is `npm ci --ignore-scripts`, so `npm ci` NEVER invokes node-gyp or any compiler — a pristine machine with no build toolchain installs successfully by construction. Enforced two ways in CI: a lockfile lint asserts zero packages declaring lifecycle install scripts or `gypfile`, and the acceptance install runs with `--ignore-scripts` on runners treated as toolchain-absent — so a dependency that would need a compiler cannot enter the tree without turning CI red. Adding a native dependency is a plan-level decision requiring Shark review, not a package.json edit.
- Update topology — persistent scrubbed release branch, append-only, ff-only: distribution is a dedicated scrubbed release repository whose `release` branch contains exactly one squashed commit per release, each commit the child of the previous release commit. The author's working history is never exported, and no rebase or history rewrite ever occurs on this branch. Deterministic commit mapping is recorded author-side only, in `release-map.json` (source SHA → release SHA, per release) at tag time. Because the branch is append-only, a collaborator's update is always a fast-forward.
- **The update transaction (`anchor update`) — the state machine.** The engine owns the WHOLE transaction; the operator types one command and zero git, on every path including every failure path. Three structural rules come first:
  - **Rollback assets are captured locally BEFORE any mutation, and rollback consumes ONLY those local assets.** The recorded vN SHA (whose objects are already in the local store), the renamed `node_modules` snapshot, the stash SHA, the moved-aside untracked/ignored files, and any exported divergent commits together make every rollback a pure local-state operation. **The network is touched at exactly two points — the step-0 fetch (before any mutation) and the step-6 `npm ci` — and no recovery path requires it.** This is the resolution of the rollback-network-fragility blocker: the previous design's rollback ran `npm ci` against the vN lockfile, which fails on the same dead network that likely broke the update; the snapshot-rename design replaces that with a rename.
  - **Diverged local commits have an explicit, engine-owned answer** (the diverged-local-commits blocker): if the collaborator has committed locally on the release branch, the engine — never the operator — exports and parks those commits (step 2 below) and proceeds; nothing is ever silently discarded (a backup branch and per-commit patches both survive), and the operator manages the parked work exclusively through `anchor edits` commands.
  - **A legitimately foundry-edited skill is local data, not drift.** The foundry path updates a skill file and its recorded hash in the local hash manifest ATOMICALLY (one Phase-2 atomic write covering both), so a sanctioned local skill edit is always hash-consistent. The transaction treats such edits exactly like any tracked local edit: captured by the step-3 stash, restored-or-parked at step 7, and — critically — the step-8 verify consults the manifest AS RESTORED, so a cleanly-restored foundry edit passes verify without being flagged as tampering, while a skill edit WITHOUT a matching manifest entry (true drift) fails verify and triggers park-and-reverify. If release vN+1 also changed the same skill, the restore conflicts and parks with a report — the collaborator's version survives as patches; nothing is silently reverted in either direction.

  Specified end-to-end against a concrete worst case — release vN+1 adds a new dependency (`ajv`, pure-JS per the policy above, enters the lockfile) and modifies `bin/engine.mjs`; the collaborator has uncommitted local edits to `bin/engine.mjs`, a foundry-edited skill (manifest updated through the sanctioned path), AND a local commit they made last week — on a Windows machine with an eager AV and no compiler:

| # | Step | What it does | Failure modes | Recovery (all offline, local-state-only) |
| --- | --- | --- | --- | --- |
| 0 | Preflight (read-only) | fetch; verify the SSH-signed tag vN+1 against the pinned allowed-signers root imported at first contact (Phase 7); verify new tip is a descendant of the recorded vN release SHA (append-only ancestry); detect local divergence (HEAD ≠ recorded vN SHA) | network down; bad signature; non-descendant tip | abort with a report — **nothing has been touched**; the only network-dependent step before mutation |
| 1 | Begin transaction | write the transaction file under the config root: recorded vN SHA, target vN+1 SHA, phase marker (updated at every step boundary) | disk full | abort; nothing touched |
| 2 | Diverged-commit capture | if local commits exist: export each as a .patch into the parked-edits area, create an engine-named local backup branch at the current HEAD, record both in the transaction file, then reset the branch ref to the recorded vN SHA (working tree preserved) | patch export failure | abort; collaborator still on their own HEAD, untouched |
| 3 | Working-tree capture | auto-stash tracked edits via engine stash-create/stash-store (stash SHA → transaction file) — in the concrete case, the `bin/engine.mjs` edit AND the foundry-edited skill+manifest pair; move aside untracked AND ignored files that collide with incoming release paths into the parked-edits area, with a report line per file | fs errors | move files back from the parked area; offline unwind of steps 3→2 |
| 4 | node_modules snapshot | rename `node_modules` → `node_modules.pre-<vN+1>` (same-volume rename — instant, atomic, offline) | Windows AV handle-hold on the directory | Phase-2 directory contention bound: backoff up to the total bound, then loud failure naming AV; offline unwind of steps 4→2 |
| 5 | Code | `git merge --ff-only origin/release` (objects already fetched in step 0 — this step is offline) — cannot conflict on the now-clean tree by construction of the append-only branch | disk | offline rollback (below) |
| 6 | Dependency sync | `npm ci --ignore-scripts` into a FRESH `node_modules` from the SHIPPED vN+1 lockfile — installs `ajv` with zero compilation by the pure-JS policy (no compiler exists on this machine, and none is needed); the ONLY post-mutation network-dependent step | registry down; network flake; interrupted mid-install; Windows AV holding files in the partial tree during cleanup | **OFFLINE ROLLBACK:** delete the partial `node_modules` under the Phase-2 directory-delete contention bound (if AV wedges the delete past the bound, the partial tree is renamed aside to `*.trash-<seq>` for deferred next-boot cleanup — the rollback proceeds either way); rename `node_modules.pre-<vN+1>` back; `git reset --hard <recorded vN SHA>` (local objects); restore moved-aside files; re-apply (or park) the stash — no step here can touch the network |
| 7 | Restore-or-park | re-apply the recorded stash. Clean apply → edits restored (in the concrete case: the engine.mjs edit and the skill+manifest pair both return). Conflicting apply (e.g. vN+1 also touched the same skill) → **park-with-report**: stash ref preserved AND exported as per-file .patch files in the parked-edits area; tree stays at stock vN+1; report names every parked file and the three engine commands — `anchor edits diff`, `anchor edits restore`, `anchor edits drop` (the same commands manage parked commits from step 2) | apply crash | idempotent redo from the phase marker; or offline rollback |
| 8 | **Verify — on the FINAL assembled tree** | doctor + Phase-6 skill-hash verification (against the manifest AS RESTORED — a cleanly-restored foundry edit passes; unmanifested drift fails) + boot smoke run on the tree **as it will actually run**: after restore/park, with vN+1 deps installed — not on a pristine intermediate. If verify fails AND local edits were restored in step 7: park them, re-verify stock vN+1. If stock vN+1 still fails verify: full offline rollback to vN | verify failure | park-and-reverify, else offline rollback — both engine-executed |
| 9 | Commit | clear the transaction file; delete the `node_modules.pre-<vN+1>` snapshot under the directory-delete contention bound (a wedged delete renames it aside for deferred next-boot cleanup — never a transaction failure); success report: restored/parked files, parked commits + backup branch name if any, stamped capability diff for vN+1 | AV handle-hold on snapshot delete | rename-aside + deferred cleanup; the transaction still commits |

  **Interrupted-resume (power loss included, at ANY marker):** the transaction file's phase marker makes the interruption detectable at next boot; the doctor offers resume-or-rollback, both engine-executed (over the local control channel or directly under the cross-process lock if the engine is down), and rollback from every marker is offline by the asset rule above. User state, config, tokens, and sessions live under the Phase-2 config root outside the repo tree, so NO step — forward, park, or rollback — can touch user data. The instance ALWAYS terminates in a working state; edits and commits are never silently lost and never block the update.
  - The promise, stated flatly: at no point on any path — success, park, divergence, rollback, interrupted-resume, wedged-AV — does the operator type a git command; every remediation surface is an `anchor` command; and the Phase-5 acceptance suite asserts mechanically that no transcript, error message, or shipped doc prescribes operator git (or openssl) after first contact.
- Adversarial leak-scan gate (idea 6 / M2): on the staged bundle — secret scanner + username/machine-name/absolute-path/email pattern scan; ONE hit is a gate failure that blocks handoff, never a patch-and-ship. The human spot-check is repositioned OUT of per-commit CI: it is an asynchronous RELEASE gate on the Phase-7 checklist, so it remains a deliberate act rather than a per-commit rubber stamp; per-commit CI runs only the machine gates (allowlist verification + scanners + smokes).
- Scrub-as-CI (idea 9 / M12): the bundle build + machine leak-scan gates run on every main-branch change in the Phase-1 CI matrix; a red bundle build has the same blocking status as a failing test.
- Staged-bundle boot smoke (idea 10): `import anchor_gui` and engine start inside the staged bundle, executed from a foreign directory root, gating every release — proves the allowlist omitted nothing load-bearing (criterion 3's smoke gate).
- Cross-skill spawn integration smoke (idea 14 / M3): from a foreign root inside the staged bundle, exercise locate-plan.mjs, the resolver CLI, and the researchPrime→Crucible import — proving the trio finds each other on a machine with a different directory layout.
- Doc-consistency checker (idea 28): asserts the shipped docs' dependency claims match the actual lockfiles/manifests, wired into the bundle build (criterion 7).

**Deferred (explicitly):**
- Signed tags + pinned-key/commit-hash verification mechanics (Phase 7 — the transaction above consumes them; Phase 7 builds them).
- Update tooling beyond the ff-only transaction specified above (no delta/binary updater, no background auto-update).
- Public distribution or any channel other than the private scrubbed release repo (trusted-collaborator model only).

## Phase 5 — Collaborator Onboarding: Doctor, Capability Probe, and First-Run Acceptance on Pristine VMs

Serves criteria 4 and 5's driver half. M8 derives the doctor checklist from REAL pristine-VM onboarding, not memory; M10 extends the release gate to a scripted full first-run loop per OS; M4 replaces the impossible 'identical models' promise with the honest stamped-capability contract. **'Pristine' is defined adversarially and pinned: the acceptance images start with no git, no gpg, no compiler toolchain, and no package manager assumed configured — every command the docs or the out-of-band message prescribe must exist on the machine at the moment it is typed, or be installed by an earlier step whose provenance (URL/installer/OS-native mechanism) the step itself states.**

**Near-term specifics:**
- Preflight doctor command (idea 11 / M8): checks every prerequisite with version bounds and prints ONE consolidated actionable fix list (not first-failure-only); its checklist is derived by actually onboarding on pristine Windows/macOS/Linux VMs and recording every stumble. The doctor also detects an interrupted Phase-4 update transaction via the transaction file and offers resume-or-rollback (both engine-executed; rollback offline). Doctor prescriptions obey the no-git-surgery rule: every remediation it prints is either an `anchor` command or an environment fix (install X from stated provenance, exclude directory Y from AV) — never a git or openssl invocation against the release tree.
- First-contact step in the onboarding doc: onboarding BEGINS with the Phase-7 integrity ceremony (install the ceremony's two tools per the out-of-band message's provenance step, pin the key, verify the tag's SSH signature, confirm the tag's commit hash against the out-of-band value — BEFORE executing anything from the clone), following ONLY the out-of-band message's instructions per Phase 7's trust-nothing-in-repo rule — the docs order it explicitly so no collaborator runs unverified code first.
- Capability probe at onboard (idea 15 / M4): prints exactly which role (Shark, Judge, Synthesizer, driver seats) resolved to which model on this host, stamps it per run; docs state the minimum viable subscription tier and what degrades below it — the deliverable contract is 'identical governance and discipline; models = best available on your subscription, stamped per run'.
- Driver-init self-configuration hardening (idea 19): driver-init probes the host's installed engines/CLIs and configures seats accordingly, logging each resolution — the same code path the author runs, exercised by the first-run scenario below.
- Scripted first-run acceptance per target OS (idea 13 / M10): in CI VMs matching the pristine definition above — first-contact ceremony from the out-of-band template (executed literally, including its tool-provenance step, proving every command exists when typed) → boot → authenticate via the Phase-3 secret-free interactive claim (spawn-journal-asserted: browser argv = [launcher, secret-free URL]; a simulated prefetch GET against the armed window is asserted NOT to consume it) → a second scenario authenticating via the headless pairing path (including one wrong-code attempt against the global per-code cap) → one WS-upgrade denial check (no cookie → refused pre-101) and one authenticated WS session → one CLI control-channel invocation (peer-identity accepted for same user; a cross-user connection attempt refused where the CI image permits simulating it) → spawn one trivial agent through the REAL driver path → one durability-cluster write/recover cycle → one `anchor update` run against a staged N+1 fixture that adds a (pure-JS) dependency, touches a locally-edited shipped file, includes a foundry-edited skill with its manifest entry, AND sits atop a locally-committed divergence — exercising diverged-commit capture (patches + backup branch), auto-stash, the node_modules snapshot rename, ff-merge, `npm ci --ignore-scripts` on the toolchain-absent image, restore-or-park, and the verify gate on the FINAL assembled tree (including the leg where a restored local edit breaks verify → auto-park → stock re-verify green, and the leg where the restored foundry edit PASSES verify via its manifest) — plus an injected step-6 failure **with the network disabled** proving the rollback to a working vN completes fully offline; the full loop must be green on Windows, macOS, and Linux before any bundle is releasable (criterion 4's gate, mechanized).
- **SSH-to-Linux-server acceptance scenario (the remote-onboarding lens made a gate):** a second-machine scenario in which the collaborator's only access to the target is SSH to a pristine Linux server — the ceremony and onboard run entirely over that SSH session (every command existing server-side when typed), `anchor pair` prints the pairing code on the server terminal, the shipped SSH-tunnel recipe is followed verbatim from the client machine (forwarded port pinned to the server port), and the claim completes from the client's browser through the tunnel. Asserted: the Origin/Host checks hold through the tunnel, the code transits exactly once in the POST body, and no step on either machine prescribes git/openssl or assumes a tool that isn't present.
- Windows first-week walkthrough (scripted, part of the acceptance suite — the operator-journey lens made a gate): three episodes on the Windows VM, each of which must terminate in a working state with zero operator-typed git/openssl — (a) a file save under a simulated AV handle-hold (the Phase-2 contention bound retries through it, or fails loudly with the AV-exclusion advice; either way the instance stays consistent), plus the directory-flavored variant: an update step-4/step-9 directory operation under the same hold, proving retry-then-rename-aside never wedges the transaction; (b) a first update with a locally tweaked shipped file AND a local commit AND a foundry-edited skill (the Phase-4 transaction captures the commit, auto-stashes the edits, restores-or-parks all of it, and the foundry edit passes final-tree verify; a tweaked CONFIG is a non-event by construction, since config lives under the config root outside the repo); (c) a first LAN-exposure attempt (any non-loopback bind is refused with the two sanctioned recipes; following the SSH-tunnel or Tailscale recipe succeeds without the operator touching openssl or seeing a certificate warning — no self-signed path exists to mis-follow). The suite asserts every transcript and error message across all three episodes prescribes only `anchor` commands or environment fixes.
- Telemetry-free default (idea 30): the collaborator bundle phones home nothing; any author-side diagnostics are opt-in and documented.

**Deferred (explicitly):**
- Automated prerequisite INSTALLATION (doctor diagnoses and prescribes with provenance; it does not install runtimes/CLIs for the user).
- Non-English onboarding docs and accessibility polish of onboarding output.
- Support matrix beyond the three named OSes (e.g. BSD, ARM-Windows) — out of scope until a collaborator needs it.

## Phase 6 — Engine-Enforced Governance Parity

Serves criterion 5. M7's principle: move load-bearing invariants from prose into cheap engine checks that run anyway, so a collaborator's instance behaves identically because the engine enforces it, not because they read the conventions.

**Near-term specifics:**
- Skill-integrity hashes (idea 16): skills ship with recorded content hashes verified at engine start (and re-verified after every update, per the Phase-4 transaction's verify step); drift → warn-and-refuse, with a documented foundry path for legitimate updates — 'skills read-only / foundry-only-edit' becomes engine-enforced. **The foundry path and the hash system are one mechanism, not two:** a sanctioned foundry edit rewrites the skill file and its manifest entry in one atomic Phase-2 write, so the manifest is always the single source of truth for 'what this instance's skills legitimately are'; boot verification, update-transaction verification (step 8, against the manifest as restored), and drift refusal all read the same manifest — which is exactly what lets a collaborator's legitimate foundry edit survive an update while unmanifested tampering is refused.
- Engine-emitted status discipline — **the hybrid** (idea 17, carried from rounds 2/3 and stated as a decision, not silently chosen): today the 10-minute status block is a prompt-side convention; this plan CHANGES it, on the author's instance first, into a two-part engine mechanism, and that change is the deliberate resolution of the NS(4)-vs-NS(5) tension. Part one — the emitter: a scheduler inside the SHARED engine (the same loop both instances run) renders the same template (timestamp, wave, budget, state) at the same cadence and the same transcript insertion point. Part two — **where the grounding instruction lives**: any instruction agents need about the status discipline (that status blocks appear on this cadence, that agents must not fabricate their own) lives in the engine's prompt-assembly layer — the driver-side preamble the engine already composes around every sub-agent invocation — versioned and shipped with the engine, hash-covered as engine code. Zero bytes of any skill file change: skills remain byte-identical and hash-verified on both instances, so the skill-immutability guarantee and the 're-architecting skill internals' non-goal are respected simultaneously. **The trade-off, named:** this accepts a deliberate NS(4) reading — 'identical to the author's' means identical to the author's instance AS IT SHIPS (both running the engine emitter), not identical to the author's pre-plan prompt-convention behavior; the author's instance adopts the hybrid BEFORE any bundle ships, so the statement is literally true at delivery. What was traded away is transcript-shape continuity with the author's historical runs — accepted, because the alternative (shipping the prompt convention and trusting collaborator-side prompt fidelity) makes NS(4) parity depend on prose, which is exactly the failure class M7 exists to kill. Against NS(5): the status block's CONTENT is sourced from the same telemetry the engine already records, so honesty is strengthened, not regressed — the block can no longer silently drift from the telemetry it reports.
- Enforcement-honesty section in shipped docs (idea 18 / M7): a plain table of which governance guarantees are engine-enforced vs convention-only, so no collaborator mistakes a norm for a mechanism.

**Deferred (explicitly):**
- Re-architecting trio/foundry skill internals (North-Star non-goal) — hashes wrap skills as-is.
- Cryptographic signing of skills (content hashes suffice for the trusted-collaborator model; signatures are Phase-7-adjacent future work).
- Runtime behavioral attestation beyond hash+status (e.g. governance conformance replay tests) — named as future hardening.

## Phase 7 — Release Integrity, the First-Contact Trust Anchor, and the External Red-Team Gate

Serves criteria 1 and 3 at the release boundary. M16's cheap insurance (signed tags + out-of-band commit-hash pinning) and M6/M9's demand for a real adversarial pass against the shipped artifact close the loop: what ships is verified, and what's verified is what was attacked. This phase also answers the hardest trust question directly: what guarantees integrity if the release repo itself is attacker-controlled at clone time?

**Near-term specifics:**
- First-contact integrity ceremony (the initial trust anchor), matched to the ACTUAL transport — a git clone of the private scrubbed release repo; there is no tarball, so there is no archive hash in this ceremony (an archive SHA-256 enters it only if a tarball channel ever ships, which none does today). The threat model assumes the repo — including every script and doc in it — may be attacker-controlled at clone time, so **nothing inside the clone can be its own root of trust, and the ceremony's instructions are NEVER taken from the repo**: not the README, not a script, not a doc — only from the out-of-band message below. Shipped docs may repeat the ceremony for convenience, but the README states verbatim that its copy is normatively void and the message governs; the acceptance suite asserts that statement is present. **The ceremony is pristine-machine honest: it needs exactly two tools — git (whose install provenance is step 0 of the payload itself) and ssh-keygen (which ships preinstalled on Windows 10/11, macOS, and mainstream Linux) — and gpg is never used, so the classic 'verify a GPG signature on a machine with no gpg' trap cannot occur. Release tags are SSH-signed (git's `gpg.format=ssh`) for exactly this reason.** The root of trust is delivered out-of-band: the author sends each collaborator, over a separate authenticated channel (a direct message on an account the collaborator already trusts as the author's), the following payload — **written out here verbatim as the shipped template** (⟨…⟩ placeholders filled per release; the collaborator runs the commands with the tools step 0 provides, in this order, before executing any file from the clone):

```bash
# 0. Prerequisites
# Git must be installed. If not, download from: https://git-scm.com/downloads (Windows) or use your OS package manager.

# 1. Establish the Trust Anchor
echo "⟨AUTHOR_EMAIL⟩ ⟨AUTHOR_PUBLIC_SSH_KEY⟩" > ~/.ssh/anchor_allowed_signers
git config --global gpg.ssh.allowedSignersFile ~/.ssh/anchor_allowed_signers

# 2. Clone and Verify
git clone ⟨RELEASE_REPO_URL⟩ anchor-instance
cd anchor-instance
git fetch --tags
git tag -v ⟨RELEASE_TAG⟩

# 3. Acceptance
# Look for: "Good \"ssh\" signature for ⟨AUTHOR_EMAIL⟩"
# If the signature is BAD, or the key does not match, delete the directory and STOP.
# Do not run anchor doctor or any other command.
```
