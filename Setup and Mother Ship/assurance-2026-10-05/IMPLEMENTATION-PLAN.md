### What each required id must establish (the executor's contract)

- cached-read-during-native-refresh — Through the real server with cookie auth: start `GET /api/provider-setup?refresh=1` on a worker thread while the native backend is blocked inside `observe` (an Event-gated fixture); then `GET /api/provider-setup`, `GET /setup` and `GET /api/provider-setup/login?id=<unknown>` each answer within a bounded time (under two seconds) with the pre-refresh cached state (auth, allowance, catalog equal to a snapshot taken before), while the refresh worker is still alive; the cached requests issued no native read (`backend.reads` unchanged by them); after release the refresh result is published (the failed metric labelled `stale` with its error).
- repeated-cached-page-load — With a realistic ledger (at least 3000 account-qualified `.json` files under `<data>/.anchor/usage_ledger`) and a native refresh held busy in the background, five consecutive authenticated loads of `/setup` plus `/api/provider-setup` each return under a generous bound; across the five loads each ledger file is opened at most once (count `builtins.open` on the ledger directory); no native command runs for a cached load; the account figures are identical across loads. Causal reproduction of the loading symptom — show the mechanism, not a timeout: (a) count the hidden native commands a cold `?refresh=1` issues when all four native CLIs are installed, by driving the real `provider_native.NativeProviders` with a counting `run_command`/`CodexAccount` substitute (capability probes, observe, catalog discovery per family), and (b) show the pre-repair cost class by instrumenting per-file ledger reads so that a repeat load pays a constant number of opens, not one per file. Record the measured counts in the execution log.
- separate-account-allowance-attribution — Two named ChatGPT connections plus the default, and two named Claude connections: allowance windows, `capacity`, `warning`, Anchor-observed ledger totals and the Claude rate-limit signal (a job record carrying `provider_connection.id` beside its log) are attributed only by connection id; a failure for one connection (timeout, expired) leaves every other connection's fresh report untouched; the legacy unqualified job log and the unqualified ledger rows attribute to nobody; a 32-hex decoy id never borrows a meter; `provider_native.account_env` for each connection names only its own home and never another family's home.
- unsupported-is-not-usable — For every unsupported shape (Claude subscription allowance `unsupported`; Grok and Gemini `unavailable`/`unsupported`; an API-mode connection; a signed-in account whose allowance report is `unknown`; `allowance_windows` fed invalid percents) the row's `capacity` is `unknown`, never `usable` or `near_limit`; `execution.ready` is false where execution is unsupported (API mode; any named Grok or Gemini connection) and `selected_for_launch` refuses it; `require_capacity_choice` does not raise for unsupported or unknown allowance (full strength retained, no silent downgrade); the server fields the UI renders (`allowance.state`, `allowance.source`, `provider_usage.state`) are explicit, and the rendered Setup text reads `Not reported`/`unsupported`, never a percentage, for such a row.
- failure-keeps-existing-session-and-quality — Across native failures (`timeout`, `expired`, `unavailable`, `error`) during refresh and a failed refresh inside `start_login`: the settings file and mirror bytes are unchanged; `provider_preferences` and `model_policy` are unchanged (full strength); a running `steward_engine.Engine` with a bound session keeps `session_id`, `provider_connection`, `model_selection` and its `_spawn_env()` home; `selected_for_launch` returns the same connection it returned before the failure (no automatic account switch); `job_runner.launch` still binds the selected account's env; in the browser, the Cave composer draft and the open Setup dialog survive a refresh failure.

### Candidate findings from the driver's pre-read (hypotheses to reproduce or refute, not approved conclusions)

Reviewers are independent; these are the orchestrating session's own reading of the code with the evidence line. Confirm each with a failing reproduction or refute it with evidence; never accept it on the driver's word.

- H1 provider_setup.py:205-207 and :260 — `ProviderService.apply` refuses every preference save while the selected account's last native observation is older than `TTL` (300 s) or failed, because `execution.ready` requires `not auth_stale`. Expected reproduction: `snapshot(True)`, then age `observations[key]["observed_at"]` past TTL (or set `auth` to `timeout`) and `apply()` a threshold-only change — `ValueError("Selected account is unready…")`. On a fresh service start the observation map is empty, so nothing can be saved before a successful native refresh. Candidate severity MAJOR (the live refresh is slow and has timed out).
- H2 provider_setup.py:262-272 — `apply` re-validates every previously saved exact quality choice against the catalog and refuses when the catalog is `stale`, even for a change that did not touch quality. Expected reproduction: save an exact model, age `catalogs[key]["observed_at"]` past TTL, `apply()` a threshold-only change — `ValueError("Refresh native model capabilities…")`. Candidate severity MAJOR.
- H3 provider_setup.py:147-154 and :162-164 — a report that was never supported (`unsupported`/`unknown`, no windows, no tokens) is stamped `observed_at`, so a later failed refresh relabels it `stale`, and the UI shows "Stale report retained" for a report that never existed. Candidate severity MINOR.
- H4 provider_native.py:54-59 with the project-file and artifact routes in anchor_gui.py and report_viewer.py:395-403 — `private_account_path` covers only isolated homes under the data directory; the default native homes (`~/.codex`, `~/.claude`, `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `~/.grok`) are servable through authenticated project routes when a registered project folder encloses them. Candidate severity MAJOR if reproducible through an authenticated route, else MINOR.
- H5 provider_setup.py:122-178 and :540-553 — `GET /api/provider-setup?refresh=1` runs every native command synchronously on the request thread (capability probes, observe, catalog discovery per family, two workers) with no server-side bound beyond each command's 15 s deadline and no client timeout; this is the likely cause class of the observed 17 s refresh. Not a correctness defect: measure it (repeated-cached-page-load part a) and record the count.
- H6 provider_setup.py:303-328 — a sign-in whose native login succeeded but whose follow-up status read failed is reported as "failed or timed out"; a retry is then refused as "already signed in". Candidate severity MINOR (honesty of the message).
